머리말

본서의 대상 독자는 라라벨로 한 개 이상의 실 서비스를 출시하거나 운영해 본 PHP 개발자다. 컨트롤러·라우트·Eloquent·Blade·큐·스케줄러의 기본 동작을 이해하고, composer·artisan·환경변수 분리·마이그레이션과 같은 일상 도구에 익숙하다고 가정한다. 따라서 PHP 문법, OOP, HTTP, RDBMS의 기초는 다루지 않는다.

본서는 심포니 8.0.x(2025년 11월 GA, 정기 지원 ~2026년 7월)를 PHP 8.5.5(2026년 3월) 위에서 사용한다. 데이터베이스는 PostgreSQL 16, 컨테이너 런타임은 Docker Compose v2를 사용한다. 모든 코드는 라라벨과의 1:1 대응을 의도적으로 노출하여, 기존 직관을 최단 경로로 이식하는 데 목적을 둔다.

접근 방식

본서는 100쪽이라는 분량 제약 안에서 “한 줄을 쓰는 데 충분한 맥락”을 제공하는 데 집중한다. 단편적 레퍼런스 나열을 피하기 위해, 처음부터 끝까지 하나의 프로젝트 — 작은 도서 이커머스 느린 책방 — 을 함께 빌드한다. 카탈로그·장바구니·인증·주문·관리자·운영의 6 도메인을 단일 코드베이스에서 다룬다.

1. 라라벨이 길러준 직관

본 절에서는 라라벨과 심포니의 핵심 개념을 1:1 매핑하여 정리한다. 라라벨에서 익힌 멘탈 모델을 그대로 옮길 수 있는 영역과, 추가 학습이 필요한 영역을 구분하는 것이 목적이다.

1.2 멘탈 모델의 두 가지 차이

(1) 명시적 의존성. 심포니는 정적 파사드(User::find())나 글로벌 헬퍼(request()) 사용을 권장하지 않는다. 모든 의존은 생성자 또는 메서드 인자 타입으로 선언하며, 컨테이너가 인스턴스를 주입한다. 이는 IDE 정적 분석, 단위 테스트의 더블 주입, 그리고 콜 스택 추적에 직접 이득을 준다.

(2) 컨벤션 대신 설정. 라라벨은 “규약 우선(convention over configuration)”으로 다수의 결정을 프레임워크가 미리 내린다. 심포니는 핵심 결정을 개발자에게 위임한다. 라우팅·인증 흐름·폼 처리·캐시 전략 등에서 명시적 구성이 요구된다. 초기 비용은 높지만 도메인 복잡도가 임계점을 넘으면 유지보수성에서 보상된다.

본서의 2부 이후는 이 두 차이를 코드 수준에서 구체화한다.

2. 심포니라는 풍경

심포니 프레임워크는 내부적으로 다섯 개의 핵심 컴포넌트로 구성된다. 본 절은 각 컴포넌트의 역할과 상호작용을 정리한다.

그림 1. HTTP 요청 처리에 관여하는 다섯 컴포넌트

2.1 핵심 컴포넌트

HttpKernel (symfony/http-kernel): handle(Request): Response 시그니처로 HTTP 요청 → 응답 변환을 책임진다. 모든 미들웨어·이벤트·예외 처리가 이 클래스를 중심으로 일어난다.

Router (symfony/routing): URL 패턴을 컨트롤러로 매핑한다. 컨트롤러의 #[Route] 속성, config/routes.php, 또는 별도 로더에서 라우트 정보를 수집하여 매칭한다.

ControllerResolver (symfony/http-kernel): 매칭된 컨트롤러 식별자(App\Controller\Foo::action 또는 invokable 클래스)를 실제 객체와 메서드 참조로 해석한다. ArgumentResolver가 메서드 인자를 채운다.

DependencyInjection Container (symfony/dependency-injection): 모든 서비스 인스턴스의 단일 출처. 컴파일 단계에서 그래프가 검증되어 런타임 오류 위험이 감소한다.

EventDispatcher (symfony/event-dispatcher): 요청 처리의 각 단계(kernel.request, kernel.controller, kernel.view, kernel.response, kernel.terminate, kernel.exception)에서 등록된 리스너를 호출한다.

2.2 라라벨과의 대응

라라벨의 Illuminate\Foundation\Http\Kernel + 미들웨어 파이프라인이 심포니의 HttpKernel + EventDispatcher 조합에 해당한다. 단, 심포니는 미들웨어 추상을 제공하지 않으며, 동일한 결과를 이벤트 리스너 또는 컨트롤러 인자로 처리한다.

3. PHP 8.5라는 시대

본서는 PHP 8.5.5(2026년 3월 26일 릴리스)를 기준으로 한다. PHP 8.5는 2025년 11월 GA되었고, 보안 패치 지원은 2027년 12월까지 보장된다. 본 절은 본서에서 활용하는 8.5의 신규 기능을 정리한다.

3.1 파이프 연산자 (|>)

$slug = $title
    |> strtolower(...)
    |> trim(...)
    |> fn ($s) => str_replace(' ', '-', $s);

좌변의 값을 우변 함수의 첫 번째 인자로 전달한다. 라라벨 Str::of()->lower()->trim()->slug() 체인의 언어 차원 대응이다. 슬러그 생성, 입력 정규화, 가격 포맷팅 같은 단방향 변환에 적합하다. 다만 메서드 체인과 달리 일급 함수를 요구하므로, strtolower(...)같이 first-class callable 문법을 함께 쓴다.

3.2 clone with

$shipped = clone $order with {
    status: 'shipped',
    shippedAt: new DateTimeImmutable(),
};

객체를 복제하면서 일부 프로퍼티만 변경한다. readonly 프로퍼티에도 적용 가능하므로, 불변 객체(value object) 기반 도메인 모델링이 한층 단순해진다. 본서의 6부 주문 상태 전이 코드에서 활용한다.

3.3 그 외 주요 변경

  • URI 확장: uri 익스텐션이 RFC 3986/WHATWG URL 표준 파싱을 코어로 제공.
  • #[NoDiscard]: 반환값이 무시되면 컴파일 경고. 트랜잭션 결과·에러 객체 등에 권장.
  • Lazy Object: ReflectionClass::newLazyGhost()·newLazyProxy() 안정화. Doctrine의 프록시 객체와 같은 패턴을 사용자 코드에서 직접 구현 가능.
  • 상수 표현식: 정적 클로저와 first-class callable을 상수 정의 시 사용 가능.

본서는 위 기능을 필요한 시점에 도입한다. PHP 8.4의 property hooks와 asymmetric visibility는 심포니 8 코어가 이미 활용 중이며, 사용자 코드 예시에서도 일부 등장한다.

4. 의존성 주입의 두 풍경

본 절은 라라벨의 app()·서비스 컨테이너와 심포니의 DependencyInjection 컴포넌트를 비교한다. 두 프레임워크 모두 컨스트럭터 인젝션을 권장하지만, 컨테이너 빌드 시점과 자동화 범위가 다르다.

4.1 자동 와이어링과 자동 구성

심포니의 기본 config/services.php는 다음과 같다.

$services = $configurator->services()
    ->defaults()
        ->autowire()         // 인자 타입으로 자동 주입
        ->autoconfigure();   // 인터페이스/속성으로 태그 자동 부여

$services->load('App\\', '../src/')
    ->exclude('../src/{DependencyInjection,Entity,Kernel.php}');

autowire는 생성자 또는 메서드 인자의 타입 힌트를 보고 컨테이너에서 동일 타입의 서비스를 찾아 주입한다. autoconfigure는 클래스가 EventSubscriberInterface를 구현하면 kernel.event_subscriber 태그를, Twig\Extension\AbstractExtension을 상속하면 twig.extension 태그를 자동 부여한다. 결과적으로 사용자 코드는 인자만 선언하면 된다.

4.2 컴파일 타임 컨테이너

심포니 컨테이너는 워밍업 시점에 단일 PHP 파일로 컴파일된다(var/cache/dev/App_KernelDevDebugContainer.php). 라라벨이 런타임에 매번 바인딩을 해석하는 것과 달리, 심포니는 컴파일 시점에 그래프를 검증하므로 누락된 의존성·순환 참조가 즉시 드러난다.

컴파일은 다음 명령으로 명시 트리거할 수 있다.

$ php bin/console cache:warmup --env=prod

4.3 명시적 인자 지정

스칼라 값(환경변수, 파라미터)을 주입할 때는 #[Autowire] 속성을 사용한다.

public function __construct(
    #[Autowire('%env(SLACK_WEBHOOK)%')]
    private string $slackWebhook,
    #[Autowire(service: 'monolog.logger.order')]
    private LoggerInterface $orderLogger,
) {}

라라벨의 $this->app->when(...)->needs(...)->give(...) 체인을 클래스 시그니처 안에 선언적으로 표현한다.

5. ORM의 두 풍경

Eloquent와 Doctrine은 동일한 RDBMS 추상화 목표를 추구하지만, 서로 다른 패턴을 기반으로 한다. 본 절은 두 패턴의 차이와 그것이 코드 구조에 미치는 영향을 정리한다.

5.1 Active Record vs Data Mapper

Eloquent는 Active Record 패턴이다. 모델 클래스가 데이터(컬럼)·검색(where)·영속화(save)·관계(belongsTo)를 모두 책임진다. User::find(1)->orders()->create([...])처럼 단일 진입점에서 모든 것이 가능하다.

Doctrine은 Data Mapper 패턴이다. 책임이 세 클래스로 분리된다.

  • Entity: 도메인 객체. PHP 속성으로 매핑 메타데이터만 보유. ORM API 호출 없음.
  • Repository: 컬렉션 인터페이스. findBy(), 커스텀 쿼리 메서드 제공.
  • EntityManager: 단일 작업 단위(Unit of Work). persist(), remove(), flush() 제공.
#[ORM\Entity(repositoryClass: ProductRepository::class)]
class Product { /* 필드와 게터·세터만 */ }

class ProductRepository extends ServiceEntityRepository
{
    public function findFeatured(int $limit = 8): array { /* ... */ }
}

// 사용
$product = $repository->findFeatured(8);
$em->persist($newProduct);
$em->flush();

5.2 Unit of Work

persist()는 즉시 SQL을 실행하지 않는다. 엔티티를 “관리 상태(managed)”로 표시하고, 변경 내역을 메모리에 누적한다. flush() 시점에 EntityManager가 변경된 모든 엔티티에 대해 INSERT/UPDATE/DELETE를 한 트랜잭션으로 발행한다. 이 동작은 N+1 문제 회피와 일관성 보장에 핵심적이다.

5.3 트레이드오프

도메인이 단순한 CRUD 위주라면 Active Record가 코드량이 적다. 도메인 로직이 많거나 ORM 의존성을 격리하고 싶다면 Data Mapper가 유리하다. 본서는 두 번째 시나리오를 가정하고, 도메인 메서드를 엔티티에 집중하되 영속화는 EntityManager에 위임하는 패턴을 일관되게 사용한다.

6. 폼의 두 풍경

객체 매핑컨트롤러 수동 (fill())Form의 data_class 자동
CSRFVerifyCsrfToken 미들웨어Form 컴포넌트 자동 + 토큰 매니저
다단계세션 수동 관리Form Wizard / 세션 + 동일 FormType

6.2 표준 컨트롤러 패턴

public function __invoke(
    Request $request,
    EntityManagerInterface $em,
): Response {
    $product = new Product();
    $form = $this->createForm(ProductType::class, $product);
    $form->handleRequest($request);

    if ($form->isSubmitted() && $form->isValid()) {
        $em->persist($product);
        $em->flush();
        return $this->redirectToRoute('product_show', [
            'slug' => $product->getSlug(),
        ]);
    }
    return $this->render('product/new.html.twig', ['form' => $form]);
}

이 7행 패턴이 모든 CRUD 폼의 골격이다. handleRequest()가 메서드(GET/POST), 페이로드 바인딩, CSRF 검증, 검증 실행을 모두 처리한다. data_class => Product::class로 지정된 FormType은 폼 데이터를 $product 인스턴스에 자동 매핑한다.

6.3 폼 재사용

동일 ProductType을 “신규 등록”과 “수정”에서 그대로 사용한다. 둘 다 data_class가 Product이므로 빈 인스턴스 vs 기존 인스턴스만 다르다. 라라벨에서 StoreProduct·UpdateProduct를 쌍으로 만들던 패턴이 단일 클래스로 축약된다.

7. 환경설정의 두 풍경

심포니의 환경설정은 두 층으로 구성된다. (1) .env 파일군이 환경변수를 정의하고, (2) config/packages/*.php가 번들·컴포넌트의 동작을 선언한다. 심포니 8부터 PHP 형식이 기본이며, YAML/XML은 선택지로 남는다.

7.1 .env 로딩 순서

심포니의 Dotenv는 다음 순서로 파일을 읽으며, 뒤에 오는 정의가 앞을 덮어쓴다.

  1. .env — 모든 환경 공통. 커밋 대상.
  2. .env.local — 로컬 머신 전용 비밀. .gitignore.
  3. .env.{APP_ENV} — 환경별 (예: .env.prod). 커밋 대상.
  4. .env.{APP_ENV}.local — 환경+로컬 비밀. .gitignore.

라라벨이 단일 .env를 쓰는 것과 달리, 심포니는 “커밋되는 기본값 + 커밋되지 않는 비밀” 분리를 강제한다. 운영 환경에서는 composer dump-env prod로 모든 변수를 .env.local.php 한 파일로 컴파일하여 부트 시간을 단축한다.

7.2 PHP 기반 설정의 이점

// config/packages/twig.php

return static function (TwigConfig $twig): void {
    $twig->defaultPath('%kernel.project_dir%/templates');
    $twig->strictVariables(true);
    $twig->formThemes(['form/bootstrap_5_layout.html.twig']);
};

TwigConfig는 번들이 제공하는 타입 시그니처 클래스다. IDE 자동완성, 오타 검출, 옵션 누락 검출이 컴파일 단계에서 가능하다. 사용 가능한 옵션은 php bin/console config:dump-reference twig로 확인한다.

7.3 시크릿 관리

강한 비밀(API 키, 결제 키)은 .env 대신 Secrets Vault를 권장한다.

$ php bin/console secrets:set STRIPE_SECRET
$ php bin/console secrets:list --reveal

비밀은 config/secrets/{env}/에 공개키로 암호화되어 저장되며, 운영 서버에서만 비공개 키로 복호화된다. 라라벨의 php artisan env:encrypt와 동일한 목적.

13. 첫 컨트롤러

심포니 8.0에서 권장되는 컨트롤러 패턴은 단일 액션을 갖는 invokable 클래스다. PHP의 __invoke() 매직 메서드를 활용하여, 하나의 컨트롤러가 하나의 라우트만 책임지도록 강제한다(SRP).

13.1 표준 시그니처

final class ShowProductController extends AbstractController
{
    #[Route('/books/{slug}', name: 'product_show', methods: ['GET'])]
    public function __invoke(
        string $slug,
        ProductRepository $products,
    ): Response {
        $product = $products->findBySlug($slug)
            ?? throw $this->createNotFoundException();

        return $this->render('product/show.html.twig', [
            'product' => $product,
        ]);
    }
}

인자 해석은 ArgumentResolver가 담당한다. string $slug는 라우트 변수에서, ProductRepository는 컨테이너에서 자동 주입된다. PHP 8의 throw 표현식을 사용해 null 처리를 한 줄로 압축할 수 있다.

13.2 invokable의 이점

  • 단일 책임: 클래스명이 액션을 직접 표현 (ShowProductController, AddToCartController).
  • 서비스 식별: 라우트 컨피그에서 App\Controller\ShowProductController가 곧 서비스 ID이자 라우트의 _controller.
  • 테스트 용이: 클래스 단위로 모킹 범위가 명확.

13.3 다중 액션이 필요할 때

리소스 묶음이 명백한 경우(예: REST 컨트롤러), 다중 메서드 클래스도 가능하다. 메서드별로 #[Route]를 부여하고, 클래스 레벨 #[Route('/admin/products', name: 'admin_product_')]로 prefix를 공유한다. 본서는 단순성을 위해 invokable을 일관되게 사용한다.

14. 요청의 일생

본 절은 단일 HTTP 요청이 심포니 애플리케이션을 통과하는 전체 흐름을 단계별로 정리한다.

그림 2. HttpKernel이 단일 요청을 처리하는 흐름

14.1 단계별 이벤트

  1. kernel.request: 요청 객체가 생성된 직후. Firewall, Locale Listener가 동작.
  2. 라우팅: RouterListener가 URL을 매칭하여 _controller·_route를 Request 속성에 설정.
  3. kernel.controller: 컨트롤러 콜러블이 결정된 직후. ParamConverter, IsGranted 검사 실행.
  4. kernel.controller_arguments: 인자 해석 완료. #[MapEntity]·#[MapQueryParameter] 처리.
  5. 컨트롤러 실행: __invoke() 호출. 비즈니스 로직.
  6. kernel.view: 컨트롤러가 Response가 아닌 값을 반환한 경우 변환 (예: #[MapRequestPayload]).
  7. kernel.response: 응답 직전. 보안 헤더, 쿠키, Profiler Toolbar 주입.
  8. 전송: Response::send()로 클라이언트에 전송.
  9. kernel.terminate: 응답 후. 메일 비동기 발송, 메트릭 플러시 등 지연 작업.
  10. kernel.exception: 예외 발생 시 위 흐름을 가로채 동작. ExceptionListener가 에러 페이지 렌더.

14.2 리스너 등록 예

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\ResponseEvent;

#[AsEventListener(event: 'kernel.response', priority: -10)]
final class SecurityHeadersListener
{
    public function __invoke(ResponseEvent $event): void
    {
        $event->getResponse()->headers->set(
            'Strict-Transport-Security', 'max-age=63072000',
        );
    }
}

이벤트 우선순위는 정수이며, 큰 값이 먼저 호출된다. 동일 이벤트의 핵심 리스너 우선순위는 php bin/console debug:event-dispatcher kernel.response로 확인한다.

15.1 응답 생성

17. 도메인 — Product와 Category

본 절은 카탈로그의 도메인 모델을 정의한다. 본서의 카탈로그는 4 엔티티(Product · Category · ProductImage · Tag)를 갖는다. 첫 셋의 관계도는 다음과 같다.

그림 3. 카탈로그 도메인 모델

  • Product n : 1 Category — ManyToOne · nullable=true(미분류 허용).

18. ER 다이어그램

본 절은 카탈로그의 물리 스키마를 정리한다. 17장의 객체 모델이 RDBMS의 테이블·외래 키로 어떻게 매핑되는지를 시각화한다.

그림 4. 카탈로그 물리 스키마 (PostgreSQL 16)

18.1 키와 인덱스

  • product.slug: UNIQUE. URL 경로(/books/{slug})로 단일 행을 식별한다.
  • product.category_id: FK → category.id. ON DELETE SET NULL로 카테고리 삭제 시 미분류 처리.
  • product.created_at: 인덱스 권장. “최신순” 쿼리(ORDER BY created_at DESC)의 풀 스캔을 방지.
  • product_image.product_id: FK → product.id, ON DELETE CASCADE.
  • product_image (product_id, position): 복합 인덱스. “한 상품의 이미지를 순서대로” 쿼리 가속.

18.2 명명 규칙

Doctrine은 기본적으로 PHP 클래스명을 snake_case 테이블명으로 변환한다(ProductImage → product_image). 이름 충돌이나 예약어와의 간섭을 피하려면 #[ORM\Table(name: '...')]로 명시할 수 있다. PostgreSQL의 예약어 order, user는 반드시 다른 이름(orders, app_user)으로 매핑한다.

18.3 마이그레이션 자동 생성

본 ER을 직접 SQL로 작성하지 않는다. 19~21장에서 엔티티 클래스를 정의한 후, php bin/console make:migration으로 차분(diff)을 자동 생성한다. 22장에서 마이그레이션 파일의 구조를 검증한다.

19. Product 엔티티

본 절은 Product 엔티티 클래스를 작성한다. 매핑은 PHP 속성으로 표현하며, 검증 제약(#[Assert\*])을 같은 위치에 둔다. 이 패턴은 “한 곳에 한 번만 정의”한다는 단일 출처 원칙(SSOT)을 따른다.

// src/Entity/Product.php
namespace App\Entity;

use App\Repository\ProductRepository;
use Doctrine\ORM\Mapping as ORM;
use Symfony\Component\Validator\Constraints as Assert;

#[ORM\Entity(repositoryClass: ProductRepository::class)]
#[ORM\Index(columns: ['created_at'], name: 'ix_product_created_at')]
class Product
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 200)]
    #[Assert\NotBlank(message: '제목은 필수입니다.')]
    #[Assert\Length(max: 200)]
    private string $name = '';

    #[ORM\Column(length: 220, unique: true)]
    #[Assert\Regex('/^[a-z0-9-]+$/')]
    private string $slug = '';

    #[ORM\Column(type: 'text')]
    private string $description = '';

    #[ORM\Column]
    #[Assert\PositiveOrZero]
    private int $priceKrw = 0;

    #[ORM\Column]
    private int $stock = 0;

    #[ORM\Column(type: 'datetime_immutable')]
    private \DateTimeImmutable $createdAt;

    #[ORM\Column(type: 'datetime_immutable', nullable: true)]
    private ?\DateTimeImmutable $publishedAt = null;

    public function __construct()
    {
        $this->createdAt = new \DateTimeImmutable();
    }

    public function isAvailable(): bool
    {
        return $this->publishedAt !== null && $this->stock > 0;
    }
}

게터·세터는 make:entity Product --regenerate로 자동 생성한다. Doctrine이 프록시를 동적으로 상속하므로 final은 부착하지 않는다.

20. Category와 ManyToMany

본 절은 Category 엔티티와 Product↔Category의 ManyToMany 관계를 정의한다. 한 도서가 다중 분류(예: “시” + “한국 문학”)에 속할 수 있는 시나리오에 대응한다.

// src/Entity/Category.php
#[ORM\Entity(repositoryClass: CategoryRepository::class)]
class Category
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 80)]
    private string $name = '';

    #[ORM\Column(length: 80, unique: true)]
    private string $slug = '';

    /** @var Collection<int, Product> */
    #[ORM\ManyToMany(targetEntity: Product::class, mappedBy: 'categories')]
    private Collection $products;

    public function __construct() {
        $this->products = new ArrayCollection();
    }
}
// src/Entity/Product.php (추가)
/** @var Collection<int, Category> */
#[ORM\ManyToMany(targetEntity: Category::class, inversedBy: 'products')]
#[ORM\JoinTable(name: 'product_category')]
#[ORM\JoinColumn(name: 'product_id', onDelete: 'CASCADE')]
#[ORM\InverseJoinColumn(name: 'category_id', onDelete: 'CASCADE')]
private Collection $categories;

public function addCategory(Category $c): self
{
    if (!$this->categories->contains($c)) {
        $this->categories->add($c);
    }
    return $this;
}

20.1 owning side와 inverse side

ManyToMany에서 한 쪽은 소유측(owning side), 다른 쪽은 역측(inverse side)이다. 소유측이 조인 테이블의 INSERT/DELETE를 담당한다. 본서에서는 Product가 owning(inversedBy), Category가 inverse(mappedBy)다. $category->getProducts()->add($product) 호출만으로는 DB에 반영되지 않는 점에 주의한다. 항상 owning 측인 $product->addCategory($category)를 사용한다.

20.2 라라벨 대응

Eloquent의 $book->categories()->attach($id)·sync($ids)가 위 addCategory()·재할당 메서드에 대응한다. 차이는 sync의 “기존 항목 자동 제거” 동작이며, Doctrine에서는 컬렉션을 clear() 후 재추가하거나 명시적 diff를 적용한다.

// src/Entity/ProductImage.php
#[ORM\Entity]

#[ORM\OrderBy(['position' => 'ASC'])]

21.1 cascade 옵션

24. ProductRepository — QueryBuilder

본 절은 Doctrine QueryBuilder를 사용한 커스텀 쿼리 메서드를 정리한다. ServiceEntityRepository를 상속하면 컨테이너에 자동 등록되어 컨트롤러·서비스에서 타입 힌트만으로 주입된다.

// src/Repository/ProductRepository.php
namespace App\Repository;

use App\Entity\Category;
use App\Entity\Product;
use Doctrine\Bundle\DoctrineBundle\Repository\ServiceEntityRepository;
use Doctrine\Persistence\ManagerRegistry;

/**
 * @extends ServiceEntityRepository<Product>
 */
class ProductRepository extends ServiceEntityRepository
{
    public function __construct(ManagerRegistry $registry)
    {
        parent::__construct($registry, Product::class);
    }

    public function findBySlug(string $slug): ?Product
    {
        return $this->findOneBy(['slug' => $slug]);
    }

    public function searchByKeyword(string $q, int $limit = 50): array
    {
        return $this->createQueryBuilder('p')
            ->leftJoin('p.images', 'i')->addSelect('i')
            ->andWhere('p.name LIKE :q OR p.description LIKE :q')
            ->andWhere('p.publishedAt IS NOT NULL')
            ->setParameter('q', '%'.$q.'%')
            ->orderBy('p.createdAt', 'DESC')
            ->setMaxResults($limit)
            ->getQuery()->getResult();
    }

    public function paginate(int $page, int $perPage = 12, ?Category $cat = null): array
    {
        $qb = $this->createQueryBuilder('p')
            ->leftJoin('p.images', 'i')->addSelect('i')
            ->andWhere('p.publishedAt IS NOT NULL')
            ->orderBy('p.createdAt', 'DESC')
            ->setFirstResult(($page - 1) * $perPage)
            ->setMaxResults($perPage);
        if ($cat) {
            $qb->innerJoin('p.categories', 'c')
               ->andWhere('c = :cat')->setParameter('cat', $cat);
        }
        return $qb->getQuery()->getResult();
    }
}

모든 변수는 :placeholder와 setParameter()로 바인딩된다. addSelect('i')는 N+1 회피를 위한 FETCH JOIN이다(82장 참고).

25. 카탈로그 컨트롤러

본 절은 카탈로그 목록 페이지의 컨트롤러를 작성한다. 페이지 번호는 쿼리 파라미터로 받고, 카테고리 필터는 라우트 변수로 받는다.

// src/Controller/CatalogController.php
namespace App\Controller;

use App\Entity\Category;
use App\Repository\ProductRepository;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Attribute\MapQueryParameter;
use Symfony\Component\Routing\Attribute\Route;

final class CatalogController extends AbstractController
{
    #[Route('/books', name: 'catalog')]
    #[Route('/books/category/{slug}', name: 'catalog_by_category')]
    public function __invoke(
        ProductRepository $products,
        ?Category $category = null,
        #[MapQueryParameter] int $page = 1,
        #[MapQueryParameter] string $sort = 'recent',
    ): Response {
        $page = max(1, $page);
        $perPage = 12;

        $items = $products->paginate($page, $perPage, $category);
        $total = $products->countAvailable($category);

        return $this->render('catalog/index.html.twig', [
            'products' => $items,
            'category' => $category,
            'page' => $page,
            'perPage' => $perPage,
            'total' => $total,
            'lastPage' => (int) ceil($total / $perPage),
            'sort' => $sort,
        ]);
    }
}

25.1 인자 해석 메커니즘

  • 라우트 변수: {slug}는 EntityValueResolver가 Category를 자동 조회. ?Category(nullable) 타입이므로 미매칭 시 null.
  • 쿼리 파라미터: #[MapQueryParameter] 속성으로 ?page=3&sort=price를 인자로 변환. 타입 캐스팅(int·bool) 자동.
  • 서비스: ProductRepository는 컨테이너에서 주입.

결과적으로 컨트롤러 본체는 도메인 호출과 응답 생성만 담당한다. 입력 파싱·검증은 인자 시그니처가 선언적으로 처리한다.

27. 페이지네이션

본 절은 외부 의존 없이 페이지네이션을 구현한다. KnpPaginatorBundle 같은 라이브러리는 빠르지만 마크업·쿼리 제어가 제한적이다. 본서는 두 메서드(paginate·countAvailable)와 한 부분 템플릿으로 충분히 처리한다.

27.1 카운트 분리

// ProductRepository
public function countAvailable(?Category $cat = null): int
{
    $qb = $this->createQueryBuilder('p')
        ->select('COUNT(p.id)')
        ->andWhere('p.publishedAt IS NOT NULL');
    if ($cat) {
        $qb->innerJoin('p.categories', 'c')
           ->andWhere('c = :cat')->setParameter('cat', $cat);
    }
    return (int) $qb->getQuery()->getSingleScalarResult();
}

Doctrine의 Paginator(Doctrine\ORM\Tools\Pagination\Paginator)도 사용 가능하지만, JOIN FETCH가 포함되면 결과 행수와 엔티티 수가 달라 별도 카운트 쿼리가 필요하다. 본서는 명시적 두 쿼리 방식을 표준으로 한다.

27.2 부분 템플릿

{# templates/_pagination.html.twig #}
{% if lastPage > 1 %}
<nav class="pagination" aria-label="페이지">
  {% set window = 2 %}
  {% set start = max(1, page - window) %}
  {% set end   = min(lastPage, page + window) %}

  {% if page > 1 %}
    <a href="{{ path(route, routeParams|merge({page: page - 1})) }}">이전</a>
  {% endif %}

  {% for n in start..end %}
    {% if n == page %}
      <span aria-current="page">{{ n }}</span>
    {% else %}
      <a href="{{ path(route, routeParams|merge({page: n})) }}">{{ n }}</a>
    {% endif %}
  {% endfor %}

  {% if page < lastPage %}
    <a href="{{ path(route, routeParams|merge({page: page + 1})) }}">다음</a>
  {% endif %}
</nav>
{% endif %}

routeParams를 merge로 확장하므로, 카테고리 필터 등 기존 라우트 변수를 잃지 않는다. 접근성을 위해 aria-label·aria-current를 함께 부착한다.

28. 상품 상세 페이지

본 절은 단일 상품 상세 페이지를 두 가지 방식으로 구현한다. (1) 슬러그 수동 조회, (2) EntityValueResolver를 활용한 자동 매핑.

28.1 수동 조회 방식

final class ShowProductController extends AbstractController
{

    public function __invoke(
        string $slug,
        ProductRepository $products,
    ): Response {

            ?? throw $this->createNotFoundException();

        return $this->render('product/show.html.twig', [
            'product' => $product,
            'related' => $products->findRelatedTo($product, 4),
        ]);
    }
}

28.2 자동 매핑 방식

use Symfony\Bridge\Doctrine\Attribute\MapEntity;

final class ShowProductController extends AbstractController
{
    #[Route('/books/{slug}', name: 'product_show', methods: ['GET'])]
    public function __invoke(
        #[MapEntity(mapping: ['slug' => 'slug'])]
        Product $product,
        ProductRepository $products,
    ): Response {
        return $this->render('product/show.html.twig', [
            'product' => $product,
            'related' => $products->findRelatedTo($product, 4),
        ]);
    }
}

EntityValueResolver는 라우트 변수를 엔티티 필드에 매핑하여 자동 조회한다. 단일 변수가 PK일 때는 mapping 생략이 가능하지만, 슬러그처럼 비-PK 컬럼을 키로 쓸 때는 명시한다. 미존재 시 자동으로 404를 발생시킨다(NotFoundHttpException).

28.3 권장 사항

단일 엔티티 + 단일 표현식이면 자동 매핑이 명확하다. 다중 조건·소프트 삭제 필터·인가 검사가 결합되면 수동 조회가 가독성이 높다. 본서는 두 방식을 상황에 따라 혼용한다.

29. 검색

본 절은 검색 기능의 단계적 구현 전략을 정리한다. 데이터 규모에 따라 LIKE → 풀텍스트 인덱스 → 외부 검색 엔진의 3단계로 진화한다.

29.1 1단계: LIKE 기반

final class SearchController extends AbstractController
{
    #[Route('/search', name: 'search', methods: ['GET'])]
    public function __invoke(
        ProductRepository $products,
        #[MapQueryParameter] string $q = '',
    ): Response {
        $q = trim($q);
        $hits = $q !== '' ? $products->searchByKeyword($q) : [];

        return $this->render('search.html.twig', [
            'q' => $q,
            'hits' => $hits,
            'count' => count($hits),
        ]);
    }
}

적합 규모: 도서 ~10만 권 미만. LIKE '%q%'는 인덱스를 쓰지 못하므로 풀스캔이 발생한다. PostgreSQL의 pg_trgm 확장과 GIN 인덱스를 함께 쓰면 LIKE를 인덱스화할 수 있다.

29.2 2단계: PostgreSQL tsvector

-- 마이그레이션에 직접 작성
ALTER TABLE product ADD COLUMN search_vec tsvector;
UPDATE product SET search_vec =
  setweight(to_tsvector('simple', name), 'A') ||
  setweight(to_tsvector('simple', description), 'B');
CREATE INDEX ix_product_search ON product USING GIN (search_vec);

리포지토리에서 WHERE search_vec @@ plainto_tsquery('simple', :q)로 질의한다. 한국어는 별도 형태소 분석기가 없어 simple로 떨어뜨리되, 사전 분리된 키워드로 토큰화한다.

29.3 3단계: 외부 검색 엔진

도서 100만 권을 넘어서면 Meilisearch·OpenSearch·Algolia로 분리한다. 심포니에서는 Doctrine 이벤트 리스너 또는 Messenger를 통해 엔티티 변경을 인덱서로 비동기 전파한다(63장의 패턴과 동일). 검색 응답은 외부 엔진이 ID 목록을 반환하면 Doctrine으로 일괄 hydrate한다.

본서의 “느린 책방”은 1단계로 충분하다. 단계 전환의 신호는 EXPLAIN ANALYZE의 응답 시간이 50ms를 일관되게 넘기 시작하는 시점이다.

31. 두 가지 장바구니

본 절은 장바구니 영속성 전략을 비교한다. 이커머스에서 장바구니는 비로그인 사용자도 사용 가능해야 하므로, 단순 세션 저장과 사용자 영속화가 충돌한다.

31.1 세 가지 전략

전략저장소장점단점
A. 세션 전용PHP 세션 / Redis구현 단순, DB 부하 없음기기 간 동기 불가, 분석 불가

  • Cart 엔티티: UUID PK, owner(User nullable), status(active/checking_out/ordered/abandoned), createdAt, updatedAt.
  • CartItem 엔티티: cart ManyToOne, product ManyToOne, quantity int.
  • 유니크 제약: (cart_id, product_id)에 UNIQUE를 걸어 동일 상품이 두 행으로 분기되는 것을 방지.

31.3 운영 고려

유기 카트(abandoned cart) 정리: 30일 미사용 카트는 Scheduler가 정기 삭제(64장 패턴). 분석을 위해서는 abandoned 상태로 보존 후 분석 ETL로 이관한다. 본서의 구현은 단순화하여 active·ordered 두 상태만 사용한다.

32. Cart 도메인

본 절은 Cart 도메인을 세 클래스(Cart·CartItem·CartFactory)로 분리하고 책임을 정의한다.

그림 5. 장바구니 도메인 모델

32.1 책임 분배

  • Cart: 항목 추가·제거·수량 변경의 도메인 규칙을 보유. 합계 계산(totalKrw()), 항목 수(itemCount()), 상태 전이(markCheckingOut()·markOrdered()) 메서드 제공.
  • CartItem: 단일 라인. quantity 증감 메서드와 subtotalKrw() 제공. quantity = 0으로의 변경은 부모 Cart의 항목 제거 트리거.
  • CartFactory: 현재 사용자(또는 게스트)에 해당하는 활성 Cart를 단일 진입점으로 반환. 컨트롤러는 항상 이 팩토리를 통해 Cart를 얻는다.

32.2 도메인 메서드 vs 영속화

Cart 클래스 자체는 EntityManager를 알지 못한다. $cart->addItem($p, 2)는 메모리 내 변경이며, 실제 DB 반영은 컨트롤러 또는 도메인 서비스에서 $em->flush()로 일괄 처리한다. 이 분리는 두 가지 이점을 준다.

  1. 테스트 가능성: Cart의 도메인 메서드를 DB 없이 단위 테스트할 수 있다.
  2. 일관성: 한 요청 내 다수 변경이 한 트랜잭션으로 묶인다.

32.3 합계 계산 위치

합계는 Cart의 메서드로 한 번만 정의한다. 컨트롤러·템플릿·결제 흐름 어디서든 동일 메서드를 호출한다. 가격 정책 변경 시 한 곳만 수정하면 된다. 37장에서 Krw 값 객체를 도입해 정수 연산의 의미를 강화한다.

34. CartFactory — 손님과 회원

본 절은 “현재 카트” 조회를 단일 진입점으로 캡슐화한다. 컨트롤러는 사용자 인증 상태를 알 필요 없이 $factory->current($user) 한 줄로 카트를 얻는다.

// src/Cart/CartFactory.php
namespace App\Cart;

use App\Entity\{Cart, User};
use App\Repository\CartRepository;
use Doctrine\ORM\EntityManagerInterface;
use Symfony\Component\HttpFoundation\RequestStack;

final readonly class CartFactory
{
    public function __construct(
        private CartRepository $carts,
        private EntityManagerInterface $em,
        private RequestStack $requests,
    ) {}

    public function current(?User $user): Cart
    {
        if ($user) {
            return $this->carts->findActiveFor($user) ?? $this->openFor($user);
        }
        return $this->currentGuest();
    }

    private function currentGuest(): Cart
    {
        $session = $this->requests->getSession();
        $id = $session->get('cart_id');
        if ($id && ($cart = $this->carts->find($id)) && $cart->isActive()) {
            return $cart;
        }
        $cart = new Cart(owner: null);
        $this->em->persist($cart);
        $this->em->flush();
        $session->set('cart_id', (string) $cart->getId());
        return $cart;
    }

    private function openFor(User $user): Cart
    {
        $cart = new Cart(owner: $user);
        $this->em->persist($cart);
        $this->em->flush();
        return $cart;
    }
}

UUID v7 PK를 사용하여 게스트 카트 ID를 쿠키에 노출해도 시퀀스 번호 추측을 차단한다. symfony/uid 컴포넌트의 Uuid::v7()은 시간 정렬 가능한 UUID를 제공하여 인덱스 효율도 보장한다.

35. 담기

본 절은 “장바구니에 담기” 컨트롤러를 구현한다. CSRF 보호, 재고 검증, 도메인 메서드 호출의 세 단계를 거친다.

final class AddToCartController extends AbstractController
{
    #[Route('/cart/add/{slug}', name: 'cart_add', methods: ['POST'])]
    public function __invoke(
        Product $product,
        Request $request,
        CartFactory $factory,
        EntityManagerInterface $em,
        #[MapEntity(mapping: ['slug' => 'slug'])] // 슬러그 자동 매핑
    ): Response {
        $token = $request->request->get('_token');
        if (!$this->isCsrfTokenValid('cart-add-'.$product->getId(), $token)) {
            throw $this->createAccessDeniedException();
        }
        $qty = max(1, min(99, (int) $request->request->get('qty', 1)));

        if ($product->getStock() < $qty) {
            $this->addFlash('error', '재고가 부족합니다.');
            return $this->redirectToRoute('product_show', [
                'slug' => $product->getSlug(),
            ]);
        }

        $cart = $factory->current($this->getUser());
        $cart->addItem($product, $qty);
        $em->flush();

        $this->addFlash('success', '장바구니에 담았습니다.');
        return $this->redirectToRoute('cart_show');
    }
}

35.1 폼 토큰 사용

장바구니 담기는 외부 사이트에서 CSRF로 트리거될 수 있는 부작용 작업이다. 상품 상세 페이지의 폼에서 {{ csrf_token('cart-add-' ~ product.id) }}로 토큰을 발급하고, 컨트롤러가 동일 ID로 검증한다.

36. 빼기와 수량 변경

본 절은 카트 수량 일괄 갱신을 한 폼 + 한 컨트롤러로 처리한다. 사용자는 카트 페이지에서 모든 항목의 수량을 동시에 수정하고, 0으로 설정한 항목은 자동 제거된다.

final class UpdateCartController extends AbstractController
{
    #[Route('/cart/update', name: 'cart_update', methods: ['POST'])]
    public function __invoke(
        Request $request,
        CartFactory $factory,
        EntityManagerInterface $em,
    ): Response {
        if (!$this->isCsrfTokenValid('cart-update', $request->request->get('_token'))) {
            throw $this->createAccessDeniedException();
        }

        $cart = $factory->current($this->getUser());
        $changes = $request->request->all('qty');  // ['12' => '3', '17' => '0']

        foreach ($changes as $itemId => $qty) {
            $cart->setQuantity((int) $itemId, (int) $qty);
        }

        $em->flush();
        $this->addFlash('success', '장바구니를 갱신했습니다.');
        return $this->redirectToRoute('cart_show');
    }
}

// Cart::setQuantity()
public function setQuantity(int $itemId, int $qty): void
{
    $item = $this->items->findFirst(

38. 장바구니 머지

본 절은 로그인 시점에 게스트 카트를 사용자 카트로 머지한다. InteractiveLoginEvent 리스너로 구현한다.

// src/EventListener/MergeCartOnLogin.php
namespace App\EventListener;

use App\Cart\CartMerger;
use App\Entity\User;
use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpFoundation\RequestStack;
use Symfony\Component\Security\Http\Event\InteractiveLoginEvent;

#[AsEventListener]
final readonly class MergeCartOnLogin
{
    public function __construct(
        private CartMerger $merger,
        private RequestStack $requests,
    ) {}

    public function __invoke(InteractiveLoginEvent $event): void
    {
        $user = $event->getAuthenticationToken()->getUser();
        if (!$user instanceof User) return;
        $session = $this->requests->getSession();
        if ($guestId = $session->get('cart_id')) {
            $this->merger->mergeGuestInto($guestId, $user);
            $session->remove('cart_id');
        }
    }
}

38.1 머지 정책

final readonly class CartMerger
{
    public function __construct(
        private CartRepository $carts,
        private EntityManagerInterface $em,
    ) {}

    public function mergeGuestInto(string $guestId, User $user): void
    {
        $guest = $this->carts->find($guestId);
        if (!$guest || $guest->getOwner() !== null) return;

        $userCart = $this->carts->findActiveFor($user)
            ?? $this->carts->openFor($user);
        foreach ($guest->getItems() as $item) {
            $userCart->addItem($item->getProduct(), $item->getQuantity());
        }
        $this->em->remove($guest);
        $this->em->flush();
    }
}

동일 상품은 addItem()이 수량을 합산한다.

class Cart
{
    /** @return CartItem[] 재고가 부족한 항목 */
    public function itemsExceedingStock(): array
    {
        $exceeded = [];
        foreach ($this->items as $item) {
            if ($item->getQuantity() > $item->getProduct()->getStock()) {
                $exceeded[] = $item;
            }
        }
        return $exceeded;
    }

    public function isReadyForCheckout(): bool
    {
        return !$this->items->isEmpty()
            && $this->itemsExceedingStock() === [];
    }
}

42. Symfony Security 풍경

본 절은 Symfony Security의 컴포넌트와 이들의 상호작용을 정리한다. 인증(authentication)과 인가(authorization)는 분리된 추상이며, 각각 별도 컴포넌트가 책임진다.

그림 7. Security 컴포넌트 구조

42.1 컴포넌트 책임

  • User (UserInterface): 신원을 표현. getUserIdentifier()·getRoles()·eraseCredentials()를 구현.
  • UserProvider: 식별자(이메일·사용자명)로 User를 로드. Doctrine 기반 또는 LDAP·in-memory 사용 가능.
  • PasswordHasher: 비밀번호 해싱(bcrypt·argon2id·auto) · 검증.
  • Authenticator: 요청에서 자격증명 추출 → User 로드 → 비밀번호 검증 → Token 생성. 표준 구현(FormLogin·HttpBasic·JsonLogin·RememberMe) 또는 커스텀.
  • Token: 인증된 사용자 + 권한을 보유. TokenStorage에 보관.
  • Voter: 인가 결정. 속성(view·edit)과 주체(엔티티 인스턴스)를 받아 boolean 반환.
  • Firewall: 요청 패턴별로 위 흐름을 활성/비활성. config/packages/security.php에 선언.

42.2 라라벨 매핑

라라벨의 Auth::guard() · Auth::user()가 Symfony의 Security·TokenStorage에 대응한다. 라라벨 Gate·Policy가 Symfony Voter에 대응한다. 라라벨 middleware('auth')가 Symfony firewall + access_control에 대응한다.

44. 비밀번호 해싱

44.1 해싱 설정

// config/packages/security.php
$sec->passwordHasher(PasswordAuthenticatedUserInterface::class)
    ->algorithm('auto')      // 'bcrypt' | 'argon2id' | 'sodium' | 'auto'
    ->cost(13);              // bcrypt cost

use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;

#[Route('/register', name: 'register')]
final class RegisterController extends AbstractController
{
    public function __invoke(
        Request $request,
        UserPasswordHasherInterface $hasher,
        EntityManagerInterface $em,
    ): Response {

        $form = $this->createForm(RegisterType::class, $user);
        $form->handleRequest($request);

}

46.2 동작 원리

로그인 컨트롤러는 폼 화면만 렌더한다. 폼 제출(POST /login)은 컨트롤러에 도달하지 않는다. FormLoginAuthenticator가 kernel.request 단계에서 가로채 다음을 수행한다.

  1. POST 페이로드에서 email·password·_csrf_token 추출.
  2. UserProvider로 User 로드.
  3. PasswordHasher로 비밀번호 검증.
  4. 성공 → Token 생성, defaultTargetPath로 리다이렉트.
  5. 실패 → loginPath로 리다이렉트, 세션에 마지막 입력 보관.

로그아웃도 동일하게 LogoutListener가 가로챈다. 컨트롤러의 throw는 라우팅이 등록되지 않았을 때만 실행되는 안전장치다.

47. security.php 핵심

본 절은 보안 구성 파일의 구조를 정리한다. 4개 블록(passwordHasher·provider·firewall·accessControl)이 핵심이다.

// config/packages/security.php
use Symfony\Component\Security\Core\User\PasswordAuthenticatedUserInterface;
use Symfony\Config\SecurityConfig;

return static function (SecurityConfig $sec): void {
    $sec->passwordHasher(PasswordAuthenticatedUserInterface::class)
        ->algorithm('auto');

    $sec->provider('app_user_provider')
        ->entity()->class(User::class)->property('email');

    // 개발 도구는 firewall 제외
    $sec->firewall('dev')
        ->pattern('^/(_(profiler|wdt)|css|images|js)/')
        ->security(false);

    $main = $sec->firewall('main');
    $main->lazy(true)
         ->provider('app_user_provider')
         ->formLogin()
            ->loginPath('login')->checkPath('login')
            ->defaultTargetPath('home')
            ->enableCsrf(true);
    $main->logout()->path('logout')->target('home');
    $main->rememberMe()
         ->secret('%kernel.secret%')
         ->lifetime(604800)         // 7일
         ->sameSite('lax');

    $sec->accessControl()->path('^/admin')->roles(['ROLE_ADMIN']);
    $sec->accessControl()->path('^/orders')->roles(['ROLE_USER']);
};

47.1 핵심 옵션

  • lazy: true: 익명 페이지에서 세션 로드를 지연. 정적 캐싱 가능.
  • enableCsrf: true: 로그인 폼 자체에 CSRF 토큰 강제.
  • rememberMe: 영구 쿠키 발급. secret은 토큰 서명 키.
  • accessControl: 정규식 매칭. 위에서부터 첫 매칭이 적용된다.

48. ROLE 관리

본 절은 ROLE 기반 권한 모델을 다룬다. ROLE은 단순 문자열이며, ROLE_ 접두사가 강제된다(미준수 시 보안 컴포넌트가 무시).

48.1 ROLE 계층

// config/packages/security.php
$sec->roleHierarchy('ROLE_ADMIN', ['ROLE_USER']);
$sec->roleHierarchy('ROLE_ADMIN_PRODUCT', ['ROLE_USER']);
$sec->roleHierarchy('ROLE_ADMIN_ORDER',   ['ROLE_USER']);
$sec->roleHierarchy('ROLE_OWNER', [
    'ROLE_ADMIN', 'ROLE_ADMIN_PRODUCT', 'ROLE_ADMIN_ORDER',
]);

계층 선언은 가산적(additive)이다. ROLE_OWNER 보유자는 자동으로 모든 하위 ROLE을 가진다. 검사 시 한 단계만이 아니라 전이적 계층이 모두 평가된다.

48.2 기본 ROLE 부여

// User::getRoles() — 모든 사용자에 ROLE_USER 자동 보장
public function getRoles(): array
{
    return array_unique([...$this->roles, 'ROLE_USER']);
}

48.3 ROLE 변경 명령

// src/Command/PromoteAdminCommand.php
#[AsCommand(name: 'app:promote-admin', description: '사용자에게 ROLE_ADMIN 부여')]
final class PromoteAdminCommand
{
    public function __construct(
        private UserRepository $users,
        private EntityManagerInterface $em,
    ) {}

    public function __invoke(SymfonyStyle $io, string $email): int
    {
        $user = $this->users->findOneBy(['email' => $email])
            ?? throw new \RuntimeException("$email 없음");
        $user->setRoles(array_unique([...$user->getRoles(), 'ROLE_ADMIN']));
        $this->em->flush();
        $io->success("$email → ROLE_ADMIN 부여 완료");
        return 0;
    }
}

50. Voter — 도메인 권한

본 절은 Voter를 사용한 인스턴스 단위 인가 결정을 다룬다. ROLE만으로는 표현할 수 없는 “이 사용자가 이 객체를 볼 수 있는가” 같은 질문에 답한다.

// src/Security/OrderVoter.php
namespace App\Security;

use App\Entity\{Order, User};
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Authorization\Voter\Voter;

final class OrderVoter extends Voter
{
    public const VIEW = 'view';
    public const CANCEL = 'cancel';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, [self::VIEW, self::CANCEL], true)
            && $subject instanceof Order;
    }

    protected function voteOnAttribute(
        string $attribute, mixed $subject, TokenInterface $token,
    ): bool {
        $user = $token->getUser();
        if (!$user instanceof User) return false;

        $isOwner = $subject->getCustomer()->getId() === $user->getId();

        return match ($attribute) {
            self::VIEW   => $isOwner || in_array('ROLE_ADMIN_ORDER', $user->getRoles(), true),
            self::CANCEL => $isOwner && in_array($subject->getStatus(), ['pending', 'paid'], true),
        };
    }
}

50.1 호출 방법

// 컨트롤러
$this->denyAccessUnlessGranted('view', $order);
if ($this->isGranted('cancel', $order)) { /* ... */ }

// 속성으로
#[IsGranted('cancel', subject: 'order')]
public function cancel(Order $order): Response { /* ... */ }

// Twig
{% if is_granted('cancel', order) %}<button>취소</button>{% endif %}

Voter는 autoconfigure에 의해 자동 등록된다. 다중 Voter 결과는 기본적으로 “affirmative” 전략(하나라도 grant면 허용)으로 결합된다. strategy: 'unanimous'로 변경 가능.

51. 비밀번호 재설정

본 절은 비밀번호 재설정 흐름을 설계한다. 보안 결정 사항이 다수 포함되므로 전 흐름을 시퀀스로 명세한다.

그림 8. 비밀번호 재설정 흐름

51.1 보안 요구사항

  1. 사용자 열거 차단: 이메일 미존재 시에도 동일한 “이메일로 보냈다” 응답을 반환. 응답 시간도 균일화(timing attack 회피).
  2. 토큰 수명 제한: 1시간 권장. 시간 초과 시 거부.
  3. 일회성: 사용된 토큰은 즉시 무효화(used_at 컬럼 또는 행 삭제).
  4. 강한 토큰: 32바이트 이상 cryptographically random. random_bytes(32)를 base64url 인코딩.
  5. 해시 저장: DB에는 토큰 해시(SHA-256)만 저장. 평문 토큰은 이메일에만 존재.
  6. 레이트 리밋: 동일 이메일·IP에 대해 5분당 1회 제한.

51.2 권장 번들

$ composer require symfonycasts/reset-password-bundle
$ php bin/console make:reset-password

이 번들은 위 요구사항을 모두 구현한다. 자동 생성되는 코드는 RequestPasswordController·ResetPasswordController·ResetPasswordRequestType·ChangePasswordType이다.

51.3 직접 구현 시 주의

토큰을 URL 경로(/reset/{token})에 두면 Referer 헤더 누설 위험이 있다. POST 본문 또는 단명 토큰 + 별도 세션 키 조합을 권장한다. 이메일 내용에는 토큰 외에 사용자 식별 정보(이름·이메일)를 노출하지 않는다.

52. 로그아웃과 세션

본 절은 로그아웃 처리와 세션 보안 옵션을 정리한다. 세션 고정(session fixation)·CSRF·쿠키 가시성의 세 위협이 동시에 고려되어야 한다.

52.1 로그아웃 설정

// config/packages/security.php
$main->logout()
     ->path('logout')
     ->target('home')
     ->invalidateSession(true)        // 세션 데이터 전체 폐기
     ->clearSiteData(['cookies', 'storage', 'cache']);

clearSiteData는 RFC 9449의 Clear-Site-Data 헤더를 응답에 포함시켜 브라우저가 쿠키·로컬스토리지·캐시를 자동 삭제하도록 지시한다. 카트 ID 잔존 문제를 근본 차단한다.

52.2 세션 보안

// config/packages/framework.php
$framework->session()
    ->cookieLifetime(0)               // 브라우저 종료 시 만료
    ->cookieSecure(true)              // HTTPS only (운영)
    ->cookieHttpOnly(true)            // JS 접근 차단
    ->cookieSamesite('lax')           // CSRF 완화
    ->handlerId(null)                 // 기본 파일 핸들러
    ->gcMaxlifetime(3600)
    ->cookieDomain('.slow.book');     // 서브도메인 공유 시

52.3 운영 시 세션 저장소

  • 파일 (기본): 단일 서버에 적합. 서버 간 공유 불가.
  • Redis: handler_id: '%env(REDIS_URL)%'. 다중 서버에 적합.
  • RDBMS: PdoSessionHandler. 추가 인프라 불필요하지만 DB 부하 증가.

본서는 개발 환경에서 파일을, 운영에서 Redis를 권장한다. 세션 ID는 인증 시점에 자동으로 회전(session.migrate)되어 fixation을 방지한다.

53. Order 도메인

본 절은 Order 도메인의 4 엔티티(Order·OrderItem·Address·Payment)와 관계를 정의한다.

그림 9. 주문 도메인 모델

53.1 책임 분리

  • Order: 주문 헤더. 고객·상태·총액·시간·주소 참조 보유. 도메인 메서드 addItem()·markPaid()·cancel().
  • OrderItem: 주문 라인. 상품·수량·주문 시점의 단가를 보유.
  • Address: 배송지 스냅샷. 주문 시점 데이터를 그대로 보존.
  • Payment: 결제 기록. 메서드·금액·상태·게이트웨이 응답 ID. 다중 결제(부분 환불 등)를 위해 OneToMany로 확장 가능하지만 본서는 OneToOne으로 단순화.

53.2 시점 데이터의 영속화

OrderItem은 unitPriceKrw를 자체 컬럼으로 보유한다. 책 가격이 향후 변경되어도 과거 주문의 라인 가격은 그대로 보존된다. Address도 마찬가지로 사용자 주소록의 변경과 무관하게 주문 시점의 주소를 유지한다. 이 패턴은 회계 무결성의 핵심이며, 모든 이커머스 도메인에 공통 적용된다.

53.3 Order vs Cart

  • Cart는 가변: 가격은 Product에서 매 호출 조회. 항목 추가·제거 자유.
  • Order는 불변: 가격은 자체 보유. 결제 완료 후 항목 변경 불가.

이 분리 덕에 두 도메인의 동시성·트랜잭션 요구사항이 다르게 다뤄질 수 있다.

54. ER — 주문 데이터

본 절은 주문 도메인의 물리 스키마를 정리한다. 53장의 객체 모델이 4개 테이블 + 3개 외래 키로 매핑된다.

그림 10. 주문 도메인 물리 스키마

54.1 권장 인덱스

  • orders (user_id, placed_at DESC): “내 주문 내역” 쿼리(65장).
  • orders (status, placed_at): 관리자 “미배송 주문” 필터(64장 Scheduler).
  • order_item (order_id): FK이지만 명시적 인덱스 권장.
  • order_item (product_id, order_id): “이 상품을 산 주문 목록” 분석 쿼리.
  • payment (status): 부분 인덱스 WHERE status IN ('pending', 'failed')로 운영 모니터링.

54.2 시간 컬럼 표준화

모든 시간 컬럼은 TIMESTAMP WITH TIME ZONE(PostgreSQL timestamptz)로 저장한다. 애플리케이션은 DateTimeImmutable(UTC)로 다룬 후, 표시 시점에 사용자 로케일·타임존으로 변환한다. Doctrine 매핑은 type: 'datetime_immutable'이며, Y-m-d H:i:sP 형식으로 직렬화된다.

54.3 금액 컬럼 표준화

모든 금액은 최소 화폐 단위 정수로 저장한다. KRW는 1원 단위 정수, USD는 센트 정수. 컬럼명에 단위를 명시(amount_krw·unit_price_krw)하여 단위 혼합을 방지한다. 37장의 Krw 값 객체와 1:1 매핑된다.

59. Cart에서 Order로

본 절은 카트 → 주문 변환 로직을 단일 도메인 서비스(PlaceOrder)로 캡슐화한다. 이 서비스는 컨트롤러·콘솔·테스트 어디서든 동일한 진입점을 제공한다.

// src/Order/PlaceOrder.php
namespace App\Order;

use App\Entity\{Address, Cart, Order, OrderItem};
use App\Payment\GatewayInterface;
use App\Stock\StockKeeper;
use Doctrine\ORM\EntityManagerInterface;

final readonly class PlaceOrder
{
    public function __construct(
        private EntityManagerInterface $em,
        private GatewayInterface $gateway,
        private StockKeeper $stock,
    ) {}

    public function __invoke(Cart $cart, Address $address, string $method): Order
    {
        if (!$cart->isReadyForCheckout()) {
            throw new \DomainException('체크아웃 불가 카트');
        }

        // 1) 재고 차감 (락 포함, 70장)
        foreach ($cart->getItems() as $item) {
            $this->stock->decrement($item->getProduct(), $item->getQuantity());
        }

        // 2) 결제 (트랜잭션 외부, 60장)
        $idempotencyKey = (string) $cart->getId();
        $charge = $this->gateway->charge($cart->totalKrw()->amount, $method, $idempotencyKey);

        // 3) 주문 생성 + 카트 마감 (단일 트랜잭션)
        return $this->em->wrapInTransaction(function () use ($cart, $address, $charge) {
            $order = Order::fromCart($cart, $address);
            $order->markPaid($charge);
            $this->em->persist($order);
            $cart->markOrdered();
            return $order;
        });
    }
}

호출 순서가 중요하다. 재고 차감 → 결제 → 주문 영속화. 결제 후 영속화 실패 시 보상 트랜잭션(환불)이 필요하다. 이 “실패 처리” 로직은 60장에서 트랜잭션 경계와 함께 다룬다.

60. 트랜잭션 경계

본 절은 트랜잭션 경계 설계와 외부 호출의 관계를 정리한다. “외부 시스템 호출은 트랜잭션 밖”이라는 원칙을 코드 수준에서 적용한다.

60.1 wrapInTransaction

$result = $em->wrapInTransaction(function (EntityManagerInterface $em): Order {
    $em->persist($order);
    $em->persist($payment);
    return $order;
});

콜백이 정상 반환하면 flush + commit, 예외 발생 시 자동 rollback한다. 라라벨 DB::transaction()과 동일한 시맨틱이다. 콜백 내부에서 직접 flush()를 호출하지 말 것 — wrapper가 자동 처리한다.

60.2 외부 호출 격리 패턴

안티패턴:

$em->wrapInTransaction(function () use (...) {
    $em->persist($order);
    $charge = $gateway->charge(...);   // ← 트랜잭션 안에서 외부 HTTP
    $order->markPaid($charge);
});

위 코드는 결제 게이트웨이 응답이 30초 걸리면 그동안 행 락이 유지되어 다른 요청을 차단한다. 게이트웨이가 타임아웃되면 트랜잭션도 함께 롤백되어 결제 상태와 DB 상태가 어긋난다.

권장 패턴:

$charge = $gateway->charge(...);              // 1) 트랜잭션 밖

$em->wrapInTransaction(function () use ($order, $charge) {
    $order->markPaid($charge);
    $em->persist($order);                     // 2) 짧은 트랜잭션
});

60.3 결제 후 저장 실패 처리

결제 성공 후 DB 저장이 실패하는 드문 경우를 위해 보상 트랜잭션(자동 환불)을 준비한다. 실무에서는 “결제 ID + 주문 미존재” 상태를 정기 검사하는 reconciliation 잡(64장 Scheduler)이 가장 신뢰성 높은 안전망이다.

61. Workflow 컴포넌트

본 절은 Symfony Workflow를 사용해 주문 상태 머신을 단일 출처화한다. 55장에서 정의한 전이 규칙을 코드 위치 한 곳에 선언한다.

61.1 정의

// config/packages/workflow.php
return static function (FrameworkConfig $framework): void {
    $w = $framework->workflows()->workflows('order');
    $w->type('state_machine')
      ->markingStore()->property('status');
    $w->supports([Order::class])
      ->initialMarking('pending')
      ->places(['pending', 'paid', 'shipped', 'delivered', 'cancelled', 'refunding', 'refunded']);

    $w->transitions()->transition()->name('pay')
       ->from(['pending'])->to(['paid']);
    $w->transitions()->transition()->name('cancel')
       ->from(['pending'])->to(['cancelled']);
    $w->transitions()->transition()->name('ship')
       ->from(['paid'])->to(['shipped']);
    $w->transitions()->transition()->name('deliver')
       ->from(['shipped'])->to(['delivered']);
    $w->transitions()->transition()->name('request_refund')
       ->from(['paid'])->to(['refunding']);
    $w->transitions()->transition()->name('complete_refund')
       ->from(['refunding'])->to(['refunded']);
};

61.2 사용

use Symfony\Component\Workflow\WorkflowInterface;

final readonly class ShipOrder
{
    public function __construct(
        #[Target('order')] private WorkflowInterface $workflow,
    ) {}

    public function __invoke(Order $order): void
    {
        if (!$this->workflow->can($order, 'ship')) {
            throw new \DomainException('현 상태에서 출고 불가');
        }
        $this->workflow->apply($order, 'ship');
    }
}

61.3 전이 이벤트

모든 전이는 7개의 이벤트(workflow.guard·workflow.leave·workflow.transition·workflow.enter·workflow.entered·workflow.completed·workflow.announce)를 발행한다. #[AsEventListener]로 후킹하여 이메일 발송·메트릭 수집·로깅을 횡단 처리한다.

63. Messenger — 비동기 처리

본 절은 Messenger 컴포넌트로 메일 발송을 비동기화한다. 라라벨 Queue·Job 시스템과 직접 대응되며, 트랜스포트는 doctrine·amqp·redis·in-memory를 지원한다.

// src/Message/SendOrderConfirmation.php
namespace App\Message;

final readonly class SendOrderConfirmation
{
    public function __construct(public int $orderId) {}
}

// src/MessageHandler/SendOrderConfirmationHandler.php
use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
final readonly class SendOrderConfirmationHandler
{
    public function __construct(
        private OrderRepository $orders,
        private SendOrderConfirmation $sender, // 62장 서비스

    {

64. Scheduler — 정기 작업

본 절은 Scheduler 컴포넌트로 cron 기반 정기 작업을 등록한다. 라라벨 Schedule·Console\Kernel의 대응 도구이며, Messenger 위에서 동작한다.

64.1 스케줄 정의

// src/Scheduler/DailySchedule.php
namespace App\Scheduler;

use App\Message\{CheckUnshippedOrders, ReconcilePayments, CleanAbandonedCarts};
use Symfony\Component\Scheduler\Attribute\AsSchedule;
use Symfony\Component\Scheduler\{RecurringMessage, Schedule, ScheduleProviderInterface};

#[AsSchedule('default')]
final class DailySchedule implements ScheduleProviderInterface
{
    public function getSchedule(): Schedule
    {
        return (new Schedule())
            ->add(RecurringMessage::cron('0 6 * * *', new CheckUnshippedOrders()))
            ->add(RecurringMessage::cron('*/15 * * * *', new ReconcilePayments()))
            ->add(RecurringMessage::every('30 days', new CleanAbandonedCarts()))
            ->processOnlyLastMissedRun(true);
    }
}

64.2 작업 예시

  • CheckUnshippedOrders (06:00): 결제 후 3일 이상 출고되지 않은 주문 목록을 운영 채널로 알림.
  • ReconcilePayments (15분 간격): 결제 게이트웨이의 charges와 자체 DB의 payments를 대조. 60장의 보상 트랜잭션 안전망.
  • CleanAbandonedCarts (30일 간격): 30일 미사용 게스트 카트 삭제.

64.3 워커 실행

# 스케줄러 트랜스포트 워커
$ php bin/console messenger:consume scheduler_default --time-limit=3600

# 비동기 메시지 워커와 분리하여 띄울 것
$ php bin/console messenger:consume async --time-limit=3600

processOnlyLastMissedRun(true)는 워커가 다운된 동안 누락된 실행을 마지막 1회만 보충한다. 누락 보충이 불필요한 분석성 작업에 적합하다.

65. 주문 내역 조회

// src/Controller/ListMyOrdersController.php
#[Route('/orders', name: 'orders', methods: ['GET'])]

        #[MapQueryParameter] int $page = 1,
    ): Response {
        $perPage = 10;
        return $this->render('order/index.html.twig', [
            'orders' => $orders->paginateForUser(
                $this->getUser(), $page, $perPage,

            'page' => $page,

// src/Controller/ShowOrderController.php
#[Route('/orders/{id<\d+>}', name: 'order_show', methods: ['GET'])]
final class ShowOrderController extends AbstractController
{
    public function __invoke(Order $order): Response
    {

        return $this->render('order/show.html.twig', ['order' => $order]);
    }
}

65.1 인가 두 층

  • 1층 (ROLE): #[IsGranted('ROLE_USER')] — 비로그인 사용자 차단.

65.2 라우트 변수 제약

// src/Service/ImageStorage.php
final readonly class ImageStorage
{
    public function __construct(
        #[Autowire('%kernel.project_dir%/public/uploads')]
        private string $uploadDir,
        private SluggerInterface $slugger,
    ) {}

    public function store(UploadedFile $file): string
    {

    }

70. 재고 관리 — 동시성 제어

본 절은 재고 차감의 동시성 문제를 비관적 락으로 해결한다. 두 요청이 마지막 1개를 동시에 구매하려는 race condition이 핵심 시나리오다.

70.1 비관적 락 구현

// src/Stock/StockKeeper.php
namespace App\Stock;

use App\Entity\Product;
use Doctrine\DBAL\LockMode;
use Doctrine\ORM\EntityManagerInterface;

final readonly class StockKeeper
{
    public function __construct(private EntityManagerInterface $em) {}

    public function decrement(Product $product, int $qty): void
    {
        $this->em->wrapInTransaction(function () use ($product, $qty): void {
            // SELECT ... FOR UPDATE
            $this->em->lock($product, LockMode::PESSIMISTIC_WRITE);
            $this->em->refresh($product);
            if ($product->getStock() < $qty) {
                throw new InsufficientStock($product);
            }
            $product->setStock($product->getStock() - $qty);
        });
    }
}

PESSIMISTIC_WRITE는 PostgreSQL의 SELECT ... FOR UPDATE로 변환된다. 트랜잭션 종료까지 해당 행을 다른 트랜잭션이 읽기·쓰기할 수 없다. 동시 요청 중 하나는 락 해제까지 대기한다.

70.2 대안: 낙관적 락

#[ORM\Version, ORM\Column]
private int $version = 1;

버전 컬럼을 두고 UPDATE ... WHERE version = ?로 낙관적 충돌 검출. 충돌 시 OptimisticLockException이 발생하며, 애플리케이션이 재시도를 책임진다. 충돌이 드문 경우 처리량이 비관적 락보다 높다.

70.3 권장

재고처럼 동시 충돌이 빈번한 자원에는 비관적 락이 단순·안전하다. 충돌이 드문 도메인(예: 사용자 프로필)에는 낙관적 락이 효율적이다. 본서는 재고에 비관적 락을 적용한다.

71. 주문 상태 변경 인터페이스

본 절은 관리자의 주문 상태 변경 컨트롤러를 작성한다. 61장의 Workflow 컴포넌트가 잘못된 전이를 차단하고, 상태 변경 후 알림은 Messenger로 비동기화된다.

// src/Controller/Admin/OrderShipController.php
#[Route('/admin/orders/{id<\d+>}/ship', name: 'admin_order_ship', methods: ['POST'])]
#[IsGranted('ROLE_ADMIN_ORDER')]
final class OrderShipController extends AbstractController
{
    public function __invoke(
        Order $order,
        Request $request,
        #[Target('order')] WorkflowInterface $workflow,
        EntityManagerInterface $em,
        MessageBusInterface $bus,
    ): Response {
        if (!$this->isCsrfTokenValid('order-ship-'.$order->getId(),
                $request->request->get('_token'))) {
            throw $this->createAccessDeniedException();
        }
        if (!$workflow->can($order, 'ship')) {
            $this->addFlash('error', sprintf(
                '현 상태(%s)에서 출고할 수 없습니다.', $order->getStatus(),
            ));
            return $this->redirectToRoute('admin_order_show',
                ['id' => $order->getId()]);
        }

        $workflow->apply($order, 'ship');
        $order->setTrackingNumber($request->request->get('tracking'));
        $em->flush();

        $bus->dispatch(new SendShipNotification($order->getId()));

        $this->addFlash('success', '출고 처리되었습니다.');
        return $this->redirectToRoute('admin_order_show', ['id' => $order->getId()]);
    }
}

71.1 패턴 분석

  • 인가: ROLE_ADMIN_ORDER(72장의 분리된 ROLE).
  • CSRF: 주문 ID별 단일 토큰.
  • 전이 검증: $workflow->can()으로 사전 검사 — 사용자 친화 메시지 제공.
  • 비동기 알림: flush() 후 메시지 dispatch — 트랜잭션 외부.

74. Stimulus 컨트롤러

본 절은 Stimulus를 사용한 점진적 향상(progressive enhancement) 패턴을 다룬다. Hotwire의 일부이며, 마크업이 동작의 진입점을 명시한다는 점에서 Alpine.js·Vue 디렉티브와 유사하다.

74.1 컨트롤러 구조

// assets/controllers/quantity_controller.js
import { Controller } from '@hotwired/stimulus';

export default class extends Controller {
  static targets = ['input', 'subtotal'];
  static values = {
    min: { type: Number, default: 1 },
    max: { type: Number, default: 99 },
    unitPrice: Number,
  };

  connect() { this.update(); }   // 초기 렌더

  increment() { this.set(this.inputTarget.valueAsNumber + 1); }
  decrement() { this.set(this.inputTarget.valueAsNumber - 1); }

  set(n) {
    const clamped = Math.max(this.minValue, Math.min(this.maxValue, n));
    this.inputTarget.value = clamped;
    this.update();
  }

  update() {
    if (this.hasSubtotalTarget) {
      const subtotal = this.inputTarget.valueAsNumber * this.unitPriceValue;
      this.subtotalTarget.textContent = subtotal.toLocaleString() + '원';
    }
  }
}

79. 캐시 — 3 계층 전략

본 절은 심포니 애플리케이션의 캐시 계층을 정리한다. (1) 애플리케이션 캐시 · (2) HTTP 캐시 · (3) Doctrine 결과 캐시의 3계층이 함께 동작한다.

79.1 애플리케이션 캐시 (Symfony Contracts)

use Symfony\Contracts\Cache\CacheInterface;
use Symfony\Contracts\Cache\ItemInterface;

final readonly class FeaturedProducts
{
    public function __construct(
        private CacheInterface $cache,
        private ProductRepository $products,
    ) {}

    public function __invoke(): array
    {
        return $this->cache->get('featured.products',
            function (ItemInterface $item): array {
                $item->expiresAfter(600);                  // TTL
                $item->tag(['product.featured', 'catalog']); // 태그 무효화
                return $this->products->findFeatured(8);
            });
    }
}

태그 기반 무효화: $cache->invalidateTags(['product.featured']) 한 줄로 관련 모든 키 일괄 삭제. 어댑터는 config/packages/cache.php에서 정의(filesystem·redis·memcached·apcu).

79.2 HTTP 캐시

// 컨트롤러
$response = $this->render('catalog/index.html.twig', [...]);

$response->setSharedMaxAge(300);   // CDN/리버스 프록시 5분
$response->setEtag(md5($response->getContent()));
return $response;

Cloudflare·Varnish·CloudFront 같은 리버스 프록시 앞단에 두면 백엔드 요청량이 극적으로 감소한다. setEtag + $request->isNotModified()로 304 응답 처리.

82. 쿼리 성능

본 절은 Doctrine 환경의 대표적 성능 안티패턴 4가지와 대응 도구를 정리한다.

82.1 N+1 문제와 FETCH JOIN

지연 로딩 컬렉션을 반복하면 각 항목마다 추가 SELECT가 발행된다. JOIN ... ADD SELECT로 단일 쿼리화한다.

// 문제: 12개 항목 → 13 쿼리
foreach ($products as $p) { echo $p->getImages()[0]->getPath(); }

// 해결
$qb->leftJoin('p.images', 'i')->addSelect('i');   // 단일 쿼리

addSelect 누락 시 JOIN은 걸리지만 hydrate 단계에서 다시 lazy 로딩이 발생한다.

82.2 부분 객체 로딩

$qb->select('p.id', 'p.name', 'p.priceKrw')   // 필요한 컬럼만
    ->getQuery()->getArrayResult();            // 엔티티 hydrate 생략

대량 조회·통계 쿼리에서 메모리·CPU를 절약한다. 단, 결과는 일반 배열이며 도메인 메서드를 호출할 수 없다.

82.3 EntityManager clear/detach

foreach ($csv->getRows() as $i => $row) {
    $em->persist(new Product(...));
    if ($i % 100 === 0) {
        $em->flush();
        $em->clear();      // Identity Map 비움 → 메모리 회수
    }
}

대량 INSERT 시 필수 패턴. 미적용 시 메모리 사용량이 선형 증가하여 OOM이 발생한다.

82.4 진단 도구

  • Profiler (개발): /_profiler에서 페이지별 쿼리 수·시간·SQL 확인.
  • doctrine:query:sql: REPL에서 즉시 SQL 실행.
  • EXPLAIN ANALYZE: 실행 계획 분석. 인덱스 미사용 검출.
  • Blackfire: 운영 환경 프로파일링. 95퍼센타일 분석.
