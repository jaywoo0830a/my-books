머리말

본서는 라라벨·심포니 등 OOP 기반 PHP 프레임워크로 실무를 해 온 개발자가, 함수형 프로그래밍(FP)의 사고방식을 자신의 코드베이스에 점진적으로 통합하는 방법을 다룬다.

기존 FP 입문서와의 차이

대부분의 FP 입문서는 Haskell이나 Scala를 사용한다. 이는 “FP를 배우려면 별개의 언어를 익혀야 한다”는 인상을 남긴다. 본서는 그 길을 가지 않는다. PHP 8.5의 readonly 클래스, clone with, 파이프 연산자, first-class callable 같은 도구를 활용하여, 기존 OOP 코드의 일부 영역을 함수형으로 작성하는 실용적 경로를 제시한다.

  3. 함수형 패턴 — Functor · Option · Result · Monoid · Monad.

본서의 입장

본서는 OOP를 부정하지 않는다. 객체 지향의 캡슐화·다형성·상속은 여전히 강력한 도구다. 다만 도메인 계산·검증 파이프라인·이벤트 처리 같은 영역에 함수형 기법을 적용하면, 같은 OOP 코드가 더 단순하고 더 안전해진다. 본서는 그 통합의 매뉴얼이다.

1부

패러다임의 전환

1.1 상태라는 적

본 절은 가변 상태(mutable state)가 소프트웨어 복잡성의 주된 원인이라는 명제를 검토한다.

1.1.1 디버깅의 비대칭

새벽 2시. 결제 컨트롤러의 어떤 케이스에서 totalKrw가 음수가 된다. 코드를 따라가면 한 함수가 $cart를 받아 변경하고, 다른 함수가 같은 객체를 또 변경한다. 음수가 처음 나타난 시점을 찾으려면 객체의 모든 변경을 시간순으로 재구성해야 한다. 코드를 “공간적”으로 읽어서는 답이 나오지 않고, “시간적”으로 추적해야 한다.

이 비대칭은 OOP 코드베이스에 보편적으로 존재한다. 객체가 메서드 호출로 자신의 상태를 변경하고, 그 상태가 다른 객체에 전파되며, 어느 시점의 객체 상태를 알려면 그 객체가 받아온 모든 호출의 이력을 머릿속에 시뮬레이션해야 한다.

1.1.2 가변 상태의 4가지 비용

  1. 디버깅 비용 — 변경 시점·주체·결과의 3원 추적이 필요.
  2. 동시성 비용 — 같은 객체를 여러 컨텍스트가 동시에 변경하면 race condition.
  3. 테스트 비용 — 결과가 이전 상태에 의존하므로 정밀한 setup/teardown 필요.
  4. 추론 비용 — 한 줄의 의미가 주변 컨텍스트에 의존.

1.1.3 함수형의 약속

두 가지를 약속한다. (1) 같은 입력은 같은 출력. (2) 변경 대신 새로운 값을 만든다. 이 두 약속만 일관되게 지키면 위 4가지 비용이 동시에 줄어든다. 본서의 모든 기법은 결국 이 두 약속을 PHP에서 구현하는 방법이다.

1.3 함수형의 네 가지 핵심

함수형 프로그래밍은 여러 기법의 집합이지만, 그 중심에는 4가지 원리가 있다. 본서의 나머지 부분은 이 4가지의 구체적 적용이다.

1.3.1 Immutability — 불변성

한 번 생성된 값은 변경되지 않는다. 변경이 필요하면 변경된 새 값을 만든다. PHP 8.1의 readonly 프로퍼티, 8.2의 readonly 클래스, 8.5의 clone with가 이를 언어 차원에서 지원한다.

1.3.2 Pure Function — 순수 함수

같은 입력은 항상 같은 출력. 외부 상태를 읽거나 변경하지 않는다(no side effect). 모든 의존성은 인자로 명시된다. 이 성질이 가능하면 함수는 참조 투명성(referential transparency)을 갖는다 — 함수 호출을 그 결과 값으로 치환해도 프로그램의 의미가 바뀌지 않는다.

1.3.3 Higher-Order Function — 고차 함수

함수를 인자로 받거나 반환하는 함수. PHP의 array_map·array_filter·array_reduce가 대표적이다. 루프와 인덱스 변수가 사라지고, 변환의 의도가 직접 표현된다.

1.3.4 Composition — 합성

작은 함수를 결합해 큰 함수를 만든다. f: A → B와 g: B → C가 있으면 합성 g ∘ f: A → C를 만들 수 있다. 데이터 파이프라인은 합성의 시각적 표현이다.

이 4가지가 본서의 “공리”다. 2부에서는 각각의 구체적 PHP 구현을, 3부에서는 이로부터 도출되는 패턴(Functor·Monoid·Monad)을 다룬다.

1.4 PHP 8.5의 함수형 도구

PHP는 7.x 이후 꾸준히 함수형 친화적 기능을 추가해 왔다. 본 절은 본서가 활용하는 PHP 8.x의 함수형 도구를 요약한다.

1.4.1 readonly 프로퍼티 (8.1)

final class Money
{
    public function __construct(
        public readonly int $amount,
        public readonly string $currency,
    ) {}
}

한 번 할당된 후 변경 불가. 객체 외부는 물론 내부 메서드에서도 재할당 차단.

1.4.2 readonly 클래스 (8.2)

final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

모든 인스턴스 프로퍼티에 readonly 자동 적용. 보일러플레이트 감소.

1.4.3 clone with (8.5)

$older = clone $user with { age: $user->age + 1 };

readonly 클래스에서 일부 필드만 변경한 새 인스턴스를 한 줄로 생성. with-메서드 패턴의 언어 차원 지원.

1.4.4 first-class callable (8.1)

$f = strtoupper(...);             // 함수를 일급 값으로
$g = $user->greet(...);           // 메서드도 마찬가지
$results = array_map($f, $names);

1.4.5 파이프 연산자 (8.5)

$slug = $title
    |> strtolower(...)
    |> trim(...)
    |> fn ($s) => str_replace(' ', '-', $s);

좌변의 값을 우변 함수의 첫 인자로 전달. 메서드 체인 없이도 변환 흐름을 위→아래로 읽힌다.

1.4.6 그 외

match 표현식 (8.0), enum (8.1), 화살표 함수 fn () => ... (7.4), nullsafe 연산자 ?-> (8.0), property hooks · asymmetric visibility (8.4). PHP는 이미 함수형 코드를 작성하기에 충분한 도구를 갖췄다.

1.5 OOP에 함수형을 더한다

본 절은 본서의 핵심 명제를 정의한다 — OOP를 버리지 말고, 함수형을 “적합한 영역”에 통합하라.

1.5.1 함수형이 빛나는 영역

  • 도메인 계산 — 가격 계산, 할인 적용, 세금 산출 등 “입력 → 출력” 변환.
  • 검증 파이프라인 — 여러 검증 단계의 조합과 단락 평가.
  • 이벤트 처리 — Event Sourcing의 상태 재구성, 이벤트 핸들러.
  • 데이터 변환 — DTO 매핑, 직렬화, 통계 집계.
  • 설정 조립 — 미들웨어 스택, 라우트 정의, 정책 결합.

1.5.2 OOP가 빛나는 영역

  • 영속성 추상화 — Repository · Active Record.
  • 의존성 관리 — DI 컨테이너, 서비스 라이프사이클.
  • 다형성 디스패치 — 인터페이스 + 구현체.
  • I/O 자원 관리 — DB 커넥션, 파일 핸들, HTTP 클라이언트.

1.5.3 통합 패턴

실무에서는 다음과 같이 결합한다.

  1. HTTP 진입점(Controller)은 OOP로 구성. 의존성은 생성자 주입.
  2. 요청 데이터를 immutable 값 객체로 변환.
  3. 도메인 계산은 순수 함수로 작성. side effect 없음.
  4. 결과를 OOP 영속성 계층(Repository)으로 전달.
  5. 응답 직렬화는 다시 함수형 변환.

이 구조는 “순수 코어 + 부수효과 경계”라 불린다(2.3에서 상세). 라라벨·심포니의 표준 컨트롤러 시그니처와 자연스럽게 결합한다.

함수형 기본기

2.1 Immutability

본 절은 PHP에서 불변 객체를 작성하는 두 패턴을 정리한다. (A) readonly + with-메서드, (B) readonly class + clone with.

2.1.1 가변 객체의 문제

// 가변: 같은 객체가 시간에 따라 다른 의미를 가짐
class User
{
    private int $age;
    public function birthday(): void { $this->age++; }  // mutation
}
$user = new User('Carl', 32);
$user->birthday();   // $user는 어디서나 33이 됨

같은 변수 $user가 코드 위치에 따라 다른 의미를 갖는다. 디버거에서 “여기서 user.age는 32일까 33일까”를 매번 추적해야 한다.

2.1.2 패턴 A — readonly + with-메서드 (PHP 8.1+)

final class User
{
    public function __construct(
        public readonly string $name,
        public readonly int $age,
    ) {}

    public function withAge(int $age): self
    {
        return new self($this->name, $age);
    }
}
$user = new User('Carl', 32);
$older = $user->withAge(33);
// $user는 여전히 32. $older는 33.

2.1.3 패턴 B — readonly class + clone with (PHP 8.5+)

final readonly class User
{
    public function __construct(
        public string $name,
        public int $age,
    ) {}
}
$user = new User('Carl', 32);
$older = clone $user with { age: 33 };
// 동일한 결과. with-메서드 보일러플레이트 제거.

2.1.4 권장

도메인 메서드(birthday(), discount())가 의미적으로 명확하면 패턴 A. 단순 필드 갱신만 필요하면 패턴 B. 본서는 두 패턴을 상황에 따라 혼용한다.

2.2 Pure Function

순수 함수는 두 조건을 만족한다. (1) 같은 입력은 항상 같은 출력. (2) 외부 상태를 읽거나 변경하지 않음 — 부수효과(side effect) 없음.

2.2.1 비교

// IMPURE — 시간에 의존
function today(): string { return date('Y-m-d'); }

// IMPURE — 부수효과 (파일 쓰기)
function log(string $msg): void {
    file_put_contents('/tmp/log', $msg, FILE_APPEND);
}

// IMPURE — 무작위
function rollDice(): int { return random_int(1, 6); }

// PURE — 인자에만 의존, 부수효과 없음
function discountAmount(int $price, float $rate): int {
    return (int) round($price * $rate);
}

2.2.2 참조 투명성

순수 함수는 “호출 → 결과”가 항상 같으므로, 코드의 함수 호출을 그 결과 값으로 치환해도 프로그램 의미가 바뀌지 않는다. 이를 referential transparency라 한다. discountAmount(10000, 0.1)은 어디서 호출되든 항상 1000을 반환하므로, 코드에서 1000으로 치환 가능하다.

2.2.3 순수 함수의 이점

이점설명
예측 가능성코드를 “공간적”으로 읽을 수 있음. 시간 의존성 없음.
테스트 용이setup/teardown 불필요. 입력만 주면 됨. mock 없음.
병렬화입력만 같으면 결과 같음. race condition 없음.
캐시 가능결과를 메모이제이션 가능.
합성 가능다른 순수 함수와 자유롭게 합성.

현실 시스템은 어딘가에서는 부수효과(DB·HTTP·파일)를 일으켜야 한다. 함수형 프로그래밍은 부수효과를 “제거”하지 않고 경계로 밀어낸다. 다음 절에서 이 패턴을 다룬다.

2.3 Side Effect와 경계

final readonly class OrderCalculator

2.4 Higher-Order Function

고차 함수(higher-order function)는 함수를 인자로 받거나 반환하는 함수다. PHP는 함수를 “first-class citizen”으로 다루므로, 변수에 담고 인자로 전달하고 반환할 수 있다.

2.4.1 PHP 표준 고차 함수 셋

$users = [
    new User('Alice', 'alice@gmail.com'),
    new User('Bob',   'bob@yahoo.com'),
    new User('Carol', 'carol@gmail.com'),
];

// FILTER — 조건을 만족하는 요소만
$gmail = array_filter($users,
    fn (User $u) => str_ends_with($u->email, '@gmail.com'));

// MAP — 각 요소를 변환
$emails = array_map(fn (User $u) => $u->email, $gmail);

// REDUCE — 누적 결합으로 단일 값
$totalLen = array_reduce($users,
    fn (int $acc, User $u) => $acc + strlen($u->name), 0);

2.4.2 명령형 vs 함수형 비교

// IMPERATIVE — 루프와 가변 변수
$squared = [];
for ($i = 0; $i < count($numbers); $i++) {
    $squared[] = $numbers[$i] * $numbers[$i];
}

// FUNCTIONAL — 의도가 직접 표현됨
$squared = array_map(fn (int $n) => $n * $n, $numbers);

차이는 단순한 줄 수가 아니다. 명령형 코드는 “어떻게”를 기술한다(루프 변수, 인덱스, 점진적 누적). 함수형 코드는 “무엇을”을 기술한다(“각 요소를 제곱”). 의도가 직접 노출되면 코드 리뷰가 빠르고 버그 가능성이 줄어든다.

2.4.3 함수를 반환하는 함수

// 부분 적용 패턴
function multiplyBy(int $factor): callable
{
    return fn (int $n) => $n * $factor;
}

$double = multiplyBy(2);
$triple = multiplyBy(3);
array_map($double, [1, 2, 3]);  // [2, 4, 6]
array_map($triple, [1, 2, 3]);  // [3, 6, 9]

이 패턴은 “공통 로직 + 변하는 파라미터” 구조에서 보일러플레이트를 제거한다.

2.5 함수 합성과 파이프라인

본 절은 작은 함수를 결합해 큰 함수를 만드는 두 패턴을 정리한다.

2.5.1 수학적 합성

f: A → B와 g: B → C가 있으면 합성 g ∘ f: A → C를 만들 수 있다.

$f = fn (int $n) => $n + 1;       // int → int
$g = fn (int $n) => "Result: $n";  // int → string

$gf = fn (int $n) => $g($f($n));   // int → string (합성)
$gf(5);  // "Result: 6"

2.5.2 파이프라인

합성을 “왼쪽에서 오른쪽”으로 읽도록 뒤집은 형태가 파이프라인이다. PHP 8.5의 |>가 이를 직접 지원한다.

$slug = $title
    |> strtolower(...)
    |> trim(...)
    |> fn ($s) => str_replace(' ', '-', $s);

2.5.3 데이터 파이프라인 (실전)

sequenceDiagram participant I as Order[] participant F as filter(byMonth) participant M as map(toAmount) participant R as reduce(sum) participant O as MonthlySummary I->>F: 30 orders F->>M: 12 orders (filtered) M->>R: [12000, 8500, ...] R->>O: 145000 (sum) Note over I,O: 데이터가 변환 단계를 흘러감
각 단계는 순수 함수
그림 2.2. filter → map → reduce 파이프라인
final class ReportGenerator
{
    public function monthlySummary(array $orders, string $month): int
    {
        $filtered = array_filter($orders,
            fn (Order $o) => $o->createdAt->format('Y-m') === $month);
        $totals = array_map(fn (Order $o) => $o->total->amount, $filtered);
        return array_reduce($totals, fn (int $a, int $t) => $a + $t, 0);
    }
}

루프도, 인덱스도, mutation도 없다. 데이터가 filter → map → reduce 파이프라인을 흘러갈 뿐이다.

2.6 Closure와 일급 함수

PHP의 Closure는 함수를 객체처럼 다룰 수 있게 하는 메커니즘이다. 변수에 담고, 인자로 전달하고, 반환하고, 외부 변수를 캡처한다.

2.6.1 Closure 표현 방식

// 1) 익명 함수 (PHP 5.3+)
$add = function (int $a, int $b): int {
    return $a + $b;
};

// 2) 화살표 함수 (PHP 7.4+) — 한 표현식만, 외부 변수 자동 캡처
$add = fn (int $a, int $b) => $a + $b;

// 3) first-class callable (PHP 8.1+) — 기존 함수/메서드를 일급 값으로
$upper = strtoupper(...);
$greet = $user->greet(...);
$factory = MyClass::create(...);

2.6.2 변수 캡처

// 익명 함수: 명시적 use
$threshold = 1000;
$expensive = function (Product $p) use ($threshold) {
    return $p->priceKrw >= $threshold;
};

// 화살표 함수: 자동 캡처 (값으로)
$threshold = 1000;
$expensive = fn (Product $p) => $p->priceKrw >= $threshold;

2.6.3 함수형 인터페이스 — Closure as Callable

PHP의 모든 callable은 Closure로 변환 가능하다. Closure::fromCallable() 또는 first-class callable 문법(...)을 사용한다.

// 같은 의미
$f = Closure::fromCallable([$user, 'greet']);
$f = $user->greet(...);
$f = fn (...$args) => $user->greet(...$args);

2.6.4 권장

함수 본문이 한 표현식이면 화살표 함수, 여러 줄이면 익명 함수, 기존 정의를 재사용하면 first-class callable. 셋 다 결과는 Closure 인스턴스다.

2.7 Immutable Collection

PHP 배열은 값 의미(value semantics)로 복사되지만, 객체 컬렉션은 그렇지 않다. 본 절은 컬렉션을 함수형으로 다루는 패턴을 정리한다.

2.7.1 PHP 배열의 값 의미

$a = [1, 2, 3];
$b = $a;          // 복사
$b[] = 4;
// $a는 [1, 2, 3], $b는 [1, 2, 3, 4]

이 동작 덕에 PHP 배열은 자연스럽게 불변 컬렉션처럼 다룰 수 있다. 단, 객체를 담은 배열은 객체 자체가 가변이면 의미가 깨진다.

2.7.2 array 함수의 비파괴성

$prices = [100, 200, 300];
$withTax = array_map(fn (int $p) => (int)($p * 1.1), $prices);
// $prices는 그대로 [100, 200, 300]
// $withTax는 [110, 220, 330]

array_map·array_filter·array_reduce·array_merge·array_slice 등은 모두 새 배열을 반환한다. array_push·sort·shuffle은 reference로 동작하므로 함수형 코드에서 회피한다.

2.7.3 객체 컬렉션 — readonly 컨테이너

final readonly class CartItems
{
    /** @param CartItem[] $items */
    public function __construct(public array $items) {}

    public function add(CartItem $item): self {
        return new self([...$this->items, $item]);
    }

    public function remove(int $index): self {
        $copy = $this->items;
        array_splice($copy, $index, 1);
        return new self($copy);
    }

    public function map(callable $f): self {
        return new self(array_map($f, $this->items));
    }

    public function totalKrw(): int {
        return array_reduce($this->items,
            fn (int $a, CartItem $i) => $a + $i->subtotalKrw(), 0);
    }
}

모든 변경 메서드가 새 인스턴스를 반환한다. 외부에서 컬렉션을 직접 수정할 방법이 없다.

2.7.4 ext-ds, illuminate/collections

PHP의 ext-ds(Sequence·Set·Map)나 라라벨의 Illuminate\Support\Collection은 chainable 메서드를 제공하지만 일부는 가변이다. 사용 시 메서드별 불변성 여부를 문서로 확인할 것.

3.1 Functor — map과 문맥

Functor는 map 메서드를 가진 컨테이너다. List, Option, Result, Future가 모두 Functor의 인스턴스다. 공통점 둘: (1) 제네릭 타입(다른 타입의 값을 담는다), (2) map 메서드(컨테이너를 유지하며 안의 값만 변환).

classDiagram class Functor~F~ { +map(callable f) Functor~B~ } class List~A~ { +map(callable f) List~B~ } class Option~A~ { +map(callable f) Option~B~ } class Result~E_A~ { +map(callable f) Result~E_B~ } Functor <|.. List Functor <|.. Option Functor <|.. Result
그림 3.1. Functor와 그 인스턴스들

3.1.1 “문맥”의 의미

  • List의 문맥: “여러 개일 수 있다”.
  • Option의 문맥: “있을 수도, 없을 수도”.
  • Result의 문맥: “성공 또는 실패”.
  • Future의 문맥: “나중에 값이 도착”.

map은 문맥을 그대로 유지한 채, 안의 값을 변환한다. “여러 개일 수 있다”는 사실은 변환 후에도 유지되고, 변환은 각 값에 적용된다.

3.1.2 Functor의 두 법칙

  1. 항등 보존: functor.map(fn ($x) => $x) ≡ functor
  2. 합성 보존: functor.map(f).map(g) ≡ functor.map(fn ($x) => g(f($x)))

법칙 2 덕에 map 호출을 줄이거나 옵티마이저가 합칠 수 있다. 사용자 정의 Functor를 만들 때는 두 법칙이 성립하는지 항상 확인한다.

3.1.3 PHP의 Functor

PHP array는 array_map을 통해 List Functor 역할을 한다. Option·Result는 사용자 정의가 필요하다(다음 두 절). Doctrine의 Collection도 map() 메서드를 제공하므로 Functor로 다룰 수 있다.

3.2 Option — null의 대체

Tony Hoare는 null을 “10억 달러짜리 실수”라 불렀다. null은 타입 시스템이 강제하지 않는 “숨은 값”이며, 모든 함수가 잠재적으로 null을 받을 수 있다는 우려를 만든다. Option(또는 Maybe)은 “있음” 또는 “없음”을 타입 수준에서 표현한다.

3.2.1 구현

/** @template A */
final readonly class Option
{
    /** @param A|null $value */
    private function __construct(
        private mixed $value,
        private bool $present,
    ) {}

    /** @template B  @param B $value  @return Option<B> */
    public static function some(mixed $value): self {
        return new self($value, true);
    }

    public static function none(): self {
        return new self(null, false);
    }

    /** @template B  @param callable(A): B $f  @return Option<B> */
    public function map(callable $f): self {
        return $this->present ? self::some($f($this->value)) : self::none();
    }

    /** @param A $default  @return A */
    public function getOrElse(mixed $default): mixed {
        return $this->present ? $this->value : $default;
    }

    public function isPresent(): bool { return $this->present; }
}

3.2.2 사용

function findUserById(int $id): Option { /* Option<User> */ }

$displayName = findUserById(42)
    ->map(fn (User $u) => $u->name)
    ->map(fn (string $n) => strtoupper($n))
    ->getOrElse('GUEST');

사용자가 없어도 map 호출은 안전하다. None이 map을 받으면 None을 그대로 반환한다. null 체크가 사라진다.

3.2.3 라라벨·심포니에서의 활용

Repository 메서드의 반환 타입을 ?User에서 Option<User>로 바꾸면, 호출 측이 명시적으로 “없을 수 있음”을 다뤄야 한다. PHP 자체에는 Option이 없으므로 Option 클래스를 직접 정의하거나 azjezz/psl·marcj/php-functional 같은 라이브러리를 사용한다.

편의상 ?T 반환 타입과 ?-> nullsafe 연산자를 그대로 쓰는 경우도 많다. 결정 기준은 “없음 처리가 코드 곳곳에 분산되는가”다 — 분산되면 Option이 정리해 준다.

3.3 Result — 예외의 대체

Result(또는 Either)는 “성공 값” 또는 “실패 정보”를 타입으로 표현한다. 예외와 달리 시그니처에 명시되며, 호출자가 처리를 강제받는다.

3.3.1 구현 (Sealed Class 패턴)

abstract readonly class Result
{
    public static function ok(mixed $v): self { return new Ok($v); }
    public static function err(mixed $e): self { return new Err($e); }
    abstract public function map(callable $f): self;
    abstract public function flatMap(callable $f): self;
}

final readonly class Ok extends Result
{
    public function __construct(public mixed $value) {}
    public function map(callable $f): Result { return Result::ok($f($this->value)); }
    public function flatMap(callable $f): Result { return $f($this->value); }
}

final readonly class Err extends Result
{
    public function __construct(public mixed $error) {}
    public function map(callable $f): Result { return $this; }
    public function flatMap(callable $f): Result { return $this; }
}

3.3.2 사용 — 예외 없는 검증 흐름

// 호출 측 — try/catch도 null 체크도 없다
$result = $service->register('alice@example.com', 'secret123');
return match (true) {
    $result instanceof Ok => new JsonResponse($result->value, 201),
    $result instanceof Err => new JsonResponse(['error' => $result->error], 400),
};

3.4 Monoid — 결합 가능한 구조

다음 연산들의 공통점은 무엇인가?

3 + 5 = 8                    // 정수 덧셈
"hello" . " world"           // 문자열 결합
true && false                // 논리 AND
[1, 2] + [3, 4]              // 배열 결합
Money::add(Money, Money)     // 금액 덧셈

세 가지 공통점: (1) 같은 종류 둘을 합치면 같은 종류 하나가 된다. (2) 결합법칙: (a*b)*c = a*(b*c). (3) “아무것도 안 하는” 항등원이 존재한다(0, 빈 문자열, true, 빈 배열, Money::zero()).

이 세 조건을 만족하는 구조를 Monoid라 부른다.

classDiagram class Monoid~A~ { +combine(A x, A y) A +empty() A } class IntSum { +combine: x + y +empty: 0 } class StringConcat { +combine: x . y +empty: '' } class MoneyAdd { +combine: x.add(y) +empty: zero(currency) } Monoid <|.. IntSum Monoid <|.. StringConcat Monoid <|.. MoneyAdd
그림 3.2. Monoid의 인스턴스들

3.4.1 구현

interface Monoid
{
    public function combine(mixed $x, mixed $y): mixed;
    public function empty(): mixed;
}

final class IntSumMonoid implements Monoid
{
    public function combine(mixed $x, mixed $y): int { return $x + $y; }
    public function empty(): int { return 0; }
}

final readonly class MoneyAddMonoid implements Monoid
{
    public function __construct(public string $currency) {}
    public function combine(mixed $x, mixed $y): Money { return $x->add($y); }
    public function empty(): Money { return Money::zero($this->currency); }
}

3.5 fold — 보편적 reduce

fold는 “여러 값을 하나로 합치는” 연산이다. 정수 합계, 문자열 결합, 카트 총액 — 표면적으로 다른 이 연산들이 사실은 같은 한 함수의 다른 인스턴스다.

3.5.1 한 함수, 여러 모노이드

/** @template A  @param A[] $list  @param Monoid<A> $m  @return A */
function fold(array $list, Monoid $m): mixed
{
    return array_reduce(
        $list,
        fn (mixed $acc, mixed $x) => $m->combine($acc, $x),
        $m->empty(),
    );
}

fold([1, 2, 3, 4, 5], new IntSumMonoid());            // 15
fold(['a', 'b', 'c'], new StringConcatMonoid());      // "abc"
fold($cartItems, new MoneyAddMonoid('KRW'));          // Money(...)

같은 fold 함수가 모노이드만 바뀌면 완전히 다른 일을 한다. 이것이 추상화의 위력이다 — 코드 중복 없이 “결합” 패턴 하나로 다양한 도메인을 다룬다.

3.5.2 array_reduce와의 관계

PHP의 array_reduce(arr, fn, init)은 fold의 일반화다. 모노이드는 “fn과 init이 함께 의미가 있는” 특수 경우. array_reduce를 호출할 때 항상 모노이드를 의식하면 코드가 정돈된다.

3.5.3 도메인 예 — 카트 총액

final readonly class Cart
{
    /** @param CartItem[] $items */
    public function __construct(public array $items) {}

    public function totalKrw(): Money
    {
        return fold(
            array_map(fn (CartItem $i) => $i->lineTotal(), $this->items),
            new MoneyAddMonoid('KRW'),
        );
    }
}

3.5.4 병렬화 가능성

모노이드의 결합법칙은 “어느 순서로 합쳐도 같다”를 보장한다. 따라서 fold를 분할 정복으로 병렬화할 수 있다 — Hadoop/Spark의 reduce가 이 원리다. 단일 PHP 프로세스에서는 직접 활용할 일이 적지만, ETL 도구를 사용할 때 모노이드 사고는 그대로 이전된다.

3.6 Monad — flatMap과 합성

Monad는 Functor에 flatMap 연산이 추가된 것이다. map이 “문맥 안의 값을 변환”한다면, flatMap은 “변환 결과 자체가 다시 문맥인 경우 중첩을 평탄화”한다.

3.6.1 map의 한계

// findUserById가 Option<User>를 반환할 때
$userId = Option::some(42);
$nested = $userId->map(fn (int $id) => findUserById($id));
// 결과: Option<Option<User>> — 중첩!

우리가 원하는 건 Option<User>이지 Option<Option<User>>가 아니다.

3.6.2 flatMap이 해결한다

final readonly class Option
{
    /** @template B  @param callable(A): Option<B> $f  @return Option<B> */
    public function flatMap(callable $f): self
    {
        return $this->present ? $f($this->value) : self::none();
    }
}

// 체이닝 — 각 단계가 실패할 수 있음
$ordersCount = Option::some(42)
    ->flatMap(fn (int $id) => findUserById($id))       // Option<User>
    ->flatMap(fn (User $u) => findOrdersByUser($u))    // Option<Order[]>
    ->map(fn (array $orders) => count($orders))         // Option<int>
    ->getOrElse(0);

한 단계라도 None을 반환하면 체인 전체가 None이 된다. if 중첩도, null 체크도, 예외도 없다.

3.6.3 Monad의 세 법칙

  1. 좌항등: unit(a).flatMap(f) ≡ f(a)
  2. 우항등: m.flatMap(unit) ≡ m
  3. 결합법칙: m.flatMap(f).flatMap(g) ≡ m.flatMap(fn ($x) => f($x).flatMap(g))

이 법칙을 만족하는 모든 “flatMap을 가진 Functor”가 Monad다. Option·Result·Future·List가 대표적이다.

3.6.4 unit과 map의 관계

Monad는 unit(값을 컨텍스트로 감싸기)과 flatMap 두 연산만 있으면 정의된다. map은 이 둘로부터 도출된다.

// map = flatMap + unit
function map(Monad $m, callable $f): Monad {
    return $m->flatMap(fn ($x) => Monad::unit($f($x)));
}

따라서 모든 Monad는 Functor다.

4.1 할인 엔진 — Cart→Cart 합성

본 절은 함수형 사고의 가장 강력한 적용 사례 하나를 다룬다. 다양한 할인 규칙(정율·정액·카테고리·조건부)을 가진 쿠폰 엔진을 함수형으로 설계한다.

4.1.1 통찰 — 할인은 함수다

전통적 OOP 설계는 Discount를 객체로 본다. 함수형 통찰은 다음과 같다.

할인은 “카트를 받아 카트를 반환하는 순수 함수”다. 시그니처: Cart → Cart. 여러 할인의 적용은 이 함수들의 합성이다.

4.1.2 할인 규칙 — Cart→Cart

interface DiscountRule { public function apply(Cart $c): Cart; }

final readonly class PercentageDiscount implements DiscountRule
{
    public function __construct(public float $rate) {}
    public function apply(Cart $c): Cart {
        return $c->withDiscount($c->subtotal()->multiply($this->rate));
    }
}

final readonly class MinimumAmount implements DiscountRule
{
    public function __construct(public Money $min, public DiscountRule $inner) {}
    public function apply(Cart $c): Cart {
        return $c->subtotal()->isLessThan($this->min)
            ? $c                          // 조건 미충족 → 원본
            : $this->inner->apply($c);
    }
}

4.1.3 합성 — fold

final readonly class DiscountEngine
{
    /** @param DiscountRule[] $rules */
    public function __construct(public array $rules) {}

    public function apply(Cart $cart): Cart {
        return array_reduce($this->rules,
            fn (Cart $c, DiscountRule $r) => $r->apply($c),
            $cart);
    }
}

여러 할인의 적용이 fold다 — 3.5의 모노이드 패턴이 도메인에 그대로 드러난다. Cart는 readonly class로 정의하며, withDiscount·subtotal은 새 인스턴스 또는 새 Money를 반환한다.

4.2 검증 파이프라인 — Result 체이닝

회원가입 같은 다단계 검증을 Result Monad의 flatMap 체이닝으로 구현한다.

4.2.1 검증 단계 — 각각 Result 반환

final class RegistrationValidator
{
    public function validateEmail(string $e): Result {
        return filter_var($e, FILTER_VALIDATE_EMAIL)
            ? Result::ok(new EmailAddress($e))
            : Result::err('Invalid email format');
    }

    public function validatePassword(string $p): Result {
        if (strlen($p) < 8) return Result::err('Password too short');
        if (!preg_match('/[A-Z]/', $p)) return Result::err('No uppercase');
        if (!preg_match('/\d/', $p)) return Result::err('No digit');
        return Result::ok(new Password($p));
    }

    public function checkEmailUnique(EmailAddress $e): Result {
        return $this->repo->exists($e)
            ? Result::err('Email already registered')
            : Result::ok($e);
    }
}

4.2.2 체이닝 — flatMap의 단락 평가

public function register(string $email, string $password): Result
{
    return $this->v->validateEmail($email)
        ->flatMap(fn (EmailAddress $e) => $this->v->checkEmailUnique($e))
        ->flatMap(fn (EmailAddress $e) => $this->v->validatePassword($password)
            ->map(fn (Password $p) => new UserRegistration($e, $p)))
        ->flatMap(fn (UserRegistration $r) => $this->repo->persist($r));
}

한 단계라도 Err를 반환하면 이후 단계는 건너뛰고 그 Err가 흘러간다. “단락 평가”가 Monad 법칙으로부터 자동 도출된다. 컨트롤러는 match로 두 결과를 분기한다 — 예외 없음, try/catch 없음.

4.2.3 다중 오류 수집

위 패턴은 “첫 오류에서 중단”한다. 모든 오류를 수집하려면 Validation Applicative(여러 Result를 병렬로 평가하고 오류 리스트로 결합)를 사용한다. 본서의 범위를 넘으므로 라이브러리(marcj/php-functional의 Validated)를 참고할 것.

4.3 Event Sourcing — fold 패턴

Event Sourcing은 함수형 사고와 자연스럽게 일치한다. 전통적 CRUD가 “현재 상태를 직접 변경”한다면, Event Sourcing은 “발생한 이벤트의 불변 목록을 유지”하고, 현재 상태는 이벤트들을 fold해서 도출한다.

현재 상태 = fold(이벤트 목록, 초기 상태, 적용 함수)
이것은 정확히 3.5의 모노이드 fold 패턴이다.

4.3.1 이벤트는 immutable 사실

interface OrderEvent { public function occurredAt(): DateTimeImmutable; }

final readonly class OrderCreated implements OrderEvent
{
    public function __construct(
        public string $orderId,
        public string $customerId,
        public DateTimeImmutable $at,
    ) {}
    public function occurredAt(): DateTimeImmutable { return $this->at; }
}

final readonly class ItemAdded implements OrderEvent
{
    public function __construct(
        public string $productId,
        public int $quantity,
        public Money $price,
        public DateTimeImmutable $at,
    ) {}
    public function occurredAt(): DateTimeImmutable { return $this->at; }
}

final readonly class PaymentReceived implements OrderEvent
{
    public function __construct(
        public Money $amount,
        public string $transactionId,
        public DateTimeImmutable $at,
    ) {}
    public function occurredAt(): DateTimeImmutable { return $this->at; }
}

4.3.2 이벤트의 의미

각 이벤트는 “과거에 일어난 사실”이다. 이름은 과거형 동사를 사용한다 — OrderCreated(만들어졌다), ItemAdded(추가되었다), PaymentReceived(받았다). “CreateOrder”(명령) 또는 “OrderCreate”(애매) 형식은 회피한다.

이벤트는 한 번 발생하면 변경되지 않는다(readonly class). 이벤트 스토어는 append-only 로그다 — UPDATE도 DELETE도 없다. 이 구조 자체가 함수형 약속(“변경하지 않는다”)의 데이터베이스 표현이다.

다음 절에서 이벤트들을 fold하여 현재 상태를 재구성하는 코드를 본다.

4.4 이벤트와 상태 재구성

sequenceDiagram participant E1 as OrderCreated participant E2 as ItemAdded(A,2) participant E3 as ItemAdded(B,1) participant E4 as PaymentReceived(4000) participant S as OrderState Note over E1,S: fold(events, empty, apply) E1->>S: status='created' E2->>S: items=[A x2] E3->>S: items=[A x2, B x1] E4->>S: status='paid', paid=4000

4.4.1 상태는 immutable

final readonly class OrderState
{
    public function __construct(
        public string $status, public array $items, public Money $totalPaid,
    ) {}

    public static function empty(): self {
        return new self('empty', [], Money::zero('KRW'));
    }

    public function apply(OrderEvent $e): self {
        return match (true) {
            $e instanceof OrderCreated =>
                new self('created', [], Money::zero('KRW')),
            $e instanceof ItemAdded => new self($this->status,
                [...$this->items, new OrderLine($e->productId, $e->quantity, $e->price)],
                $this->totalPaid),
            $e instanceof PaymentReceived =>
                new self('paid', $this->items, $this->totalPaid->add($e->amount)),
            default => $this,
        };
    }
}

4.4.2 fold로 재구성

function reconstruct(array $events): OrderState
{
    return array_reduce($events,
        fn (OrderState $s, OrderEvent $e) => $s->apply($e),
        OrderState::empty());
}

이 두 줄이 “이벤트 스트림 → 현재 상태”의 전부다.

시간 여행: reconstruct(array_slice($events, 0, $n))으로 과거 시점의 상태 재구성.

4.5.1 EventStore — 부수효과 경계

interface EventStore

final class PostgresEventStore implements EventStore
{
    public function __construct(private Connection $conn) {}

    public function loadStream(string $streamId): array { /* DB 쿼리 */ }
    public function append(string $streamId, OrderEvent $event): void { /* INSERT */ }
}

4.5.2 컨트롤러 — 순수와 부수효과의 결합

final class OrderController
{
    public function __construct(private EventStore $store) {}

    public function addItem(Request $req): JsonResponse
    {
        // (impure) 이벤트 스트림 로드
        $events = $this->store->loadStream($req->input('orderId'));

        // (PURE) 상태 재구성 + 비즈니스 규칙
        $state = reconstruct($events);
        if ($state->status === 'shipped') {
            return new JsonResponse(['error' => '배송된 주문 수정 불가'], 400);
        }

        // (PURE) 새 이벤트 생성
        $event = new ItemAdded(
            $req->input('productId'),
            (int) $req->input('quantity'),
            new Money((int) $req->input('price'), 'KRW'),
            new DateTimeImmutable(),
        );

        // (impure) 이벤트 저장
        $this->store->append($req->input('orderId'), $event);

        $newState = $state->apply($event);
        return new JsonResponse(['status' => $newState->status], 200);
    }
}

I/O는 두 줄에 격리. 나머지는 순수 함수. mock은 EventStore·Request 둘로 충분.

4.6 테스트의 단순함

함수형 코드의 가장 직접적 이득은 테스트 비용 감소다. 본 절은 4.4의 Event Sourcing 코드에 대한 테스트를 작성하며 그 차이를 본다.

4.6.1 순수 함수 테스트 — mock 없음

final class OrderStateTest extends TestCase
{
    public function test_reconstruct_from_events(): void
    {
        $now = new DateTimeImmutable('2026-05-01');
        $events = [
            new OrderCreated('o-1', 'c-1', $now),
            new ItemAdded('A', 2, new Money(1000, 'KRW'), $now),
            new ItemAdded('B', 1, new Money(2000, 'KRW'), $now),
            new PaymentReceived(new Money(4000, 'KRW'), 'tx-1', $now),
        ];
        $state = reconstruct($events);

        self::assertSame('paid', $state->status);
        self::assertCount(2, $state->items);
        self::assertEquals(new Money(4000, 'KRW'), $state->totalPaid);
    }

    public function test_empty_stream(): void
    {
        self::assertSame('empty', reconstruct([])->status);
    }
}

4.6.2 무엇이 없는가

  • mock 없음 — 테스트할 함수가 외부 의존성을 갖지 않음.
  • DB 없음 — 메모리 안의 데이터 변환만 검증.
  • setup/teardown 최소 — 각 테스트가 독립적, 상태 누수 불가능.
  • 병렬 실행 안전 — 공유 상태가 없음.
  • flaky 없음 — 시간·랜덤·외부 서비스 의존 없음.

4.6.3 부수효과 경계 테스트

컨트롤러처럼 EventStore를 호출하는 코드는 EventStore를 mock하거나 메모리 구현체를 사용한다. 단, 이 mock 작업은 경계에서 단 한 번만 발생한다. 도메인 로직은 그 안에서 mock 없이 호출된다.

final class InMemoryEventStore implements EventStore
{
    private array $streams = [];
    public function loadStream(string $id): array { return $this->streams[$id] ?? []; }
    public function append(string $id, OrderEvent $e): void { $this->streams[$id][] = $e; }
}

이 30줄짜리 메모리 구현체가 모든 컨트롤러 테스트를 가능하게 한다. mock 라이브러리도 필요 없다.

5.1 Type-Signature Diagram

Robert C. Martin은 UML for Java Programmers에서 “클래스 다이어그램을 보면 코드가 머리에 떠올라야 한다”고 썼다. 함수형 프로그래밍에는 이에 대응하는 모델이 필요하다. OOP의 기본 모델 단위가 “상태와 행위를 가진 객체”라면, FP의 기본 모델 단위는 “불변 타입과 그 사이의 순수 함수”다.

5.1.1 가장 단순한 함수형 다이어그램

가장 단순한 함수형 다이어그램은 두 타입과 그 사이의 화살표다. 이것이 하나의 함수 시그니처에 대응한다.

그림 5.1. 카트 도메인의 Type-Signature Diagram

5.1.2 OOP class diagram과의 차이

  1. 모든 필드가 readonly. 가변 필드는 다이어그램에 그리지 않는다.
  2. void 메서드 부재. 모든 메서드는 값을 반환한다. void는 부수효과의 표지.
  3. 핵심 화살표는 “타입 변환”. Cart → OrderResult가 이 다이어그램의 주제. OOP에서는 “누가 누구를 참조”가 핵심.
  4. 변경 메서드가 자기 타입 반환. withDiscount(Money) Cart — 새 Cart를 반환한다는 의미.

이 4가지를 코드 리뷰 시 점검 항목으로 삼으면, 다이어그램과 코드 사이의 1:1 대응이 깨지는 지점을 빠르게 찾는다.

5.2 Data Flow Diagram

Martin의 sequence diagram은 “객체 간 메시지 흐름”을 보여준다. 함수형의 Data Flow Diagram은 “데이터가 함수를 거쳐 어떻게 변환되는가”를 보여준다.

5.2.1 OOP sequence diagram과의 결정적 차이

OOP에서는 객체가 lifeline을 갖고 시간에 따라 상태가 변한다. FP에서는 데이터가 변하지 않는다 — 각 변환 단계마다 새 데이터가 생성될 뿐이다. 따라서 lifeline이 아니라 파이프라인이 핵심 구조다.

5.2.2 핵심 통찰 — 상태별 별도 타입

OOP에서는 하나의 Order 클래스가 여러 상태(“unpaid”, “paid”, “shipped”)를 가진다. FP에서는 각 상태가 별개의 타입이다 — UnpaidOrder, PricedOrder, PaidOrder. 타입 시스템이 잘못된 연산을 컴파일 시점에 차단한다.

UnpaidOrder에 ship()을 호출하는 것은 타입 오류다 — ship()은 PaidOrder에만 존재한다.

5.2.3 Data Flow Diagram의 4가지 규칙

  1. 데이터(타입)와 변환(함수)이 번갈아 배치된다.
  2. 각 데이터 노드는 immutable. “원본 변하지 않음”을 항상 표기.
  3. 각 함수 노드는 순수. 부수효과가 있으면 명시적으로 표기(“impure”).
  4. 분기는 sum type(Result, Option)으로 표현.

5.3.2 다이어그램과 코드의 관계

Martin은 “코드가 다이어그램보다 종종 더 명확하고 경제적”이라고 했다. FP에서도 마찬가지다 — 변환 파이프라인 자체가 이미 매우 선언적이므로, 다이어그램이 불필요한 경우가 많다. 그러나 다이어그램이 유용한 시점이 있다: (1) 동료에게 데이터 흐름을 설명할 때, (2) 중간 타입을 발견하는 설계 초기 단계, (3) pure/impure 경계를 시각화할 때.

5.4 설계 절차

OOP에서 Martin은 “행위 우선(behavior first)”을 권장한다 — sequence diagram으로 행위를 식별한 다음 클래스 구조를 도출. FP에서의 대응 절차는 “변환 우선(transformation first)”이다.

5.4.1 5단계 절차

  1. 입력 타입과 출력 타입을 정의하라. “무엇이 들어오고 무엇이 나가는가?”가 출발점. OOP의 “어떤 메시지가 오가는가?”의 함수형 대응.
  2. 중간 타입을 발견하라. 입력에서 출력까지 한 번에 가지 말 것. 의미 있는 중간 단계의 타입을 발견한다 (UnpaidOrder → PricedOrder → PaidOrder).
  3. 각 변환을 순수 함수로 정의하라. 두 인접한 타입 사이에 하나의 함수. 같은 입력은 같은 출력. 부수효과 없음.
  4. 실패 가능성을 Result/Option으로 표현하라. 변환이 실패할 수 있다면 반환 타입에 Result 또는 Option을 붙인다. 예외를 던지지 않는다.
  5. 파이프라인으로 합성하라. 개별 함수들을 map/flatMap 체이닝으로 연결한다. 부수효과는 파이프라인의 시작과 끝(경계)에만 둔다.

5.4.2 적용 예 — 회원가입 워크플로우

Step 1: 입력 = raw HTTP request, 출력 = Result<Error, RegisteredUser>.

Step 2: 중간 타입 발견 — RawInput → ValidatedInput → NewUser → RegisteredUser.

Step 3: 각 화살표가 한 함수.

// Arrow 1
function validateInput(RawInput $r): Result { /* ... */ }
// Arrow 2 — pure
function createNewUser(ValidatedInput $v): NewUser { /* ... */ }
// Arrow 3 — impure boundary (DB write)
function persist(NewUser $u, UserRepo $repo): RegisteredUser { /* ... */ }

Step 5: 파이프라인.

$result = validateInput($raw)
    ->map(fn (ValidatedInput $v) => createNewUser($v))
    ->map(fn (NewUser $u) => persist($u, $repo));
// Result<Error, RegisteredUser>

다이어그램의 화살표 셋이 코드의 함수 셋과 1:1 대응한다. 검증 실패는 Result가 자동으로 단락한다 — 사용자 객체가 만들어지지도 않고 DB 쓰기도 일어나지 않는다.

5.5 Sum Type과 Pattern Matching

Sum Type(또는 tagged union, ADT)은 “여러 변종 중 하나”를 타입으로 표현한다. PHP에는 직접 지원 문법이 없지만, 인터페이스 + final 클래스로 동등한 구조를 만든다.

5.5.1 Sum Type 표현

interface PaymentResult {}

final readonly class PaymentSuccess implements PaymentResult
{
    public function __construct(public string $transactionId, public Money $charged) {}
}

final readonly class PaymentFailure implements PaymentResult
{
    public function __construct(public string $reason, public string $errorCode) {}
}

final readonly class PaymentDeclined implements PaymentResult
{
    public function __construct(public string $reason) {}
}

핵심: 모든 변종이 final readonly이고 인터페이스만 공유. 행위(메서드)는 인터페이스에 두지 않는다 — 외부 함수가 match로 분기한다.

5.5.2 Pattern Matching

function handleResult(PaymentResult $r): JsonResponse
{
    return match (true) {
        $r instanceof PaymentSuccess =>
            new JsonResponse(['transactionId' => $r->transactionId], 201),
        $r instanceof PaymentFailure =>
            new JsonResponse(['error' => $r->reason, 'code' => $r->errorCode], 502),
        $r instanceof PaymentDeclined =>
            new JsonResponse(['error' => $r->reason], 402),
    };
}

match (true)는 PHP에서 sum type 분기를 표현하는 표준 관용구다. 컴파일러가 “누락된 변종”을 잡아주지 않으므로 PHPStan·Psalm 같은 정적 분석과 결합한다.

5.5.3 Sum Type vs 상속

축상속 (OOP 다형성)Sum Type
변종 정의서브클래스인터페이스 구현체
행위 추가인터페이스 메서드외부 match 함수
새 변종 추가새 클래스 (다른 코드 변경 없음)모든 match 갱신 필요

이 트레이드오프를 “Expression Problem”이라 부른다. 변종이 자주 추가되면 OOP, 행위가 자주 추가되면 Sum Type이 유리하다. 도메인 결과(PaymentResult 같은)는 보통 변종이 고정되고 행위가 다양해서 Sum Type이 적합하다.

6.1 Set, Function, 합성

본 절은 함수형 프로그래밍의 수학적 토대를 고등학교 수학 수준에서 시작해 정리한다.

6.1.1 집합과 함수

  • 집합 (Set): 서로 다른 원소들의 모음. 예: 정수 집합 ℤ, 문자열 집합 String.
  • 함수 (Function) f: A → B: 집합 A의 각 원소를 집합 B의 정확히 하나의 원소에 대응시키는 규칙.
  • 정의역 (Domain): 입력 집합 A.
  • 공역 (Codomain): 출력이 속하는 집합 B.
  • 치역 (Range): 실제로 출력되는 원소들의 집합 (공역의 부분집합).

프로그래밍의 함수도 같다. function greet(int $n): string은 정수 집합에서 문자열 집합으로의 함수다. 같은 입력은 항상 같은 출력 — 이것이 “순수 함수”의 조건과 일치한다.

6.1.2 함수 합성

f: A → B와 g: B → C가 있을 때, 합성 함수 g ∘ f: A → C는 “f를 먼저 적용하고 그 결과에 g를 적용”한다. 합성이 가능하려면 f의 공역과 g의 정의역이 일치해야 한다.

6.1.3 합성의 두 성질

(1) 결합법칙: h ∘ (g ∘ f) = (h ∘ g) ∘ f. 세 함수를 합성할 때 어느 둘을 먼저 합성해도 결과가 같다.

(2) 항등 함수의 존재: id_A: A → A, id_A(x) = x. 어떤 함수에도 항등 함수를 합성하면 그 함수가 그대로 유지된다 — f ∘ id_A = f = id_B ∘ f.

6.1.4 PHP 코드로

$f = fn (int $n): int => $n + 1;     // ℤ → ℤ
$g = fn (int $n): string => "[$n]";   // ℤ → String

$gf = fn (int $n): string => $g($f($n));  // 합성
$gf(5);  // "[6]"

$id = fn (mixed $x): mixed => $x;         // 항등 함수
$f(5) === $f($id(5));   // true

이 두 성질(결합법칙 + 항등)을 만족하는 “집합 + 함수” 구조를 다음 절의 Category가 일반화한다.

6.2 Category와 Functor

1940년대 Saunders Mac Lane과 Samuel Eilenberg는 서로 다른 수학 분야(위상수학·대수학·논리학)에서 같은 패턴이 반복됨을 발견했다. 그 패턴의 일반화가 Category다.

6.2.1 Category의 정의

Category는 4가지로 구성된다.

  1. 대상(object)들의 모음.
  2. 두 대상 사이의 화살표(morphism)들.
  3. 화살표들의 합성 — 결합법칙 성립.
  4. 각 대상에 “항등 화살표”가 존재.

6.1의 “집합 + 함수”는 이 4조건을 만족하므로 하나의 Category다. 이를 Set이라 부른다.

classDiagram class StringT { type: string } class IntT { type: int } class BoolT { type: bool } StringT --> IntT : strlen IntT --> IntT : square IntT --> StringT : strval StringT --> BoolT : isEmpty
그림 6.1. PHP의 타입과 함수 — 하나의 Category

6.2.2 PHP는 Category다

PHP의 타입 시스템은 4조건을 모두 만족한다.

  • 대상: 모든 타입(int, string, User, Money, ...).
  • 화살표: 타입 A에서 타입 B로의 순수 함수.
  • 합성: PHP의 함수 합성.
  • 항등: fn ($x) => $x.

이 Category를 Php라 부르자. 본서의 모든 패턴(Functor·Monoid·Monad)은 이 Category Php 안에서 일어나는 일이다.

6.2.3 Functor — 구조 보존 사상

Functor는 한 Category에서 다른 Category로, 구조를 보존하며 옮기는 것이다. “구조를 보존한다”는 두 가지를 의미한다 — (1) 대상이 대상으로 옮겨지고, (2) 화살표가 화살표로 옮겨지고, (3) 합성과 항등이 보존된다.

Php에서 Php로의 Functor를 Endofunctor라 한다. List, Option, Result가 모두 Endofunctor다 — 타입을 “리스트로 감싼 타입”으로 옮기고, 함수를 array_map으로 옮긴다. 합성이 보존된다는 사실이 3.1.2의 “Functor 법칙 2”다.

코드의 map은 “화살표를 옮기는 부분”의 구현체다. 수학적 정의가 코드 형태를 결정했다.

6.3 Monoid in Endofunctors

함수형 커뮤니티의 유명한 문장이 있다.

“A monad is just a monoid in the category of endofunctors.”
(Monad는 endofunctor의 category에서의 monoid일 뿐이다.)

이 문장은 농담처럼 인용되지만, 실제로 정확한 수학적 진술이다. 본 절은 지금까지 배운 것으로 이 문장을 해석한다.

6.3.1 Monoid와 Monad 법칙의 평행

Monoid (3.4)Monad (3.6)
결합 연산: a * bflatten: 중첩 한 겹 벗기기
항등원: e * a = aunit: 값을 컨텍스트로 감싸기
좌항등: e * a = a법칙 1: unit(a).flatMap(f) = f(a)
우항등: a * e = a법칙 2: m.flatMap(unit) = m
결합법칙: (a*b)*c = a*(b*c)법칙 3: 체이닝 순서 무관

구조가 정확히 일치한다. Monad는 Monoid의 법칙과 동일한 법칙을 따른다.

6.3.2 “어디서?” — Endofunctor의 Category

일반적 Monoid는 “값들의 집합”(정수·문자열 등) 위에서 정의된다. Monad의 Monoid 구조는 “endofunctor들의 모음” 위에서 정의된다.

endofunctor들(List·Option·Result)을 모으면 새로운 Category를 만들 수 있다. 이를 “endofunctor의 category”라 한다. 이 category 안에서 하나의 endofunctor(예: Option)를 골라, flatten을 결합 연산으로, unit을 항등원으로 삼으면 — Monoid의 법칙이 성립한다. 이것이 Monad다.

6.3.3 문장 해석

  • “a monoid” — 결합 연산(flatten)과 항등원(unit)이 있고 결합법칙이 성립하는 구조.
  • “in the category of endofunctors” — List·Option·Result 같은 endofunctor들이 이루는 Category 안에서.
  • “A monad is just...” — 둘을 합치면 monad다.

이 문장을 이해한 순간, Functor·Monoid·Monad가 하나의 그림으로 연결된다. 표면적으로 다른 “map을 가진 컨테이너”·“결합 가능한 값”·“flatMap을 가진 컨테이너”가 사실은 같은 추상의 다른 시각이다.

이 책의 모든 코드는 이 추상의 PHP 차원의 구체화다.
